## Product gate (M11): independently owned customer plant — done

The implemented engineering seam was demonstrated only from inside this Cargo workspace until this gate landed: `dcs-build` examples emitted model documents into `dcs-demo` fixtures, and the checked-in rig mounted those repository-relative files. Decision 79 and `WW-ENG-003` made the missing product boundary explicit, and the gate proved that a plant is an external consumer of a released DCS platform, not another platform crate or fixture.

Plan the gate as narrow ordered slices:

1. Define and produce the versioned consumer release set: supported Rust engineering packages, `dcs-model`/`dcs-controller --check` tooling, the generic controller image, model/schema compatibility policy, and immutable version or digest references. Development-only path dependencies may remain inside the platform workspace, but no external acceptance may use them. **Done (#348)** — `docs/release-contract.md` records the contract (decisions 80, 81): the release set (`dcs-build` plus the `dcs-core`/`dcs-model` transitive surface, the `dcs-model` CLI and emitted JSON Schema, `dcs-controller --check`, the `dcs-controller`/`dcs-plant-server` images, and the deployment-manifest shape), git tag/rev and image-digest pins, the single-workspace-version `v<semver>` scheme with `v0.1.0` as the first release, and the model/checkpoint/fingerprint/0.x-semver compatibility policy. `crates/dcs-build/tests/consumer_release.rs` proves the pin mechanism: an out-of-workspace crate resolves the supported crates through a git pin with no path dependency, emits a byte-deterministic model, and passes validate/lint/`--check`, with the named `pin-unresolvable` diagnostic for a bad pin. The first tag itself is a supervisor git operation.
2. Create an independent reference-plant template/repository owning its Rust composition, site parameters, generated model, simulation dynamics and scenarios, operator-layout data where declared, and deployment manifest. Start with the water pumping station rather than inventing another process. **Done (#351)** — `reference-plant/` is a self-contained consumer tree (its own `[workspace]`, no path dependencies): the duty/standby station composed in `src/station.rs` from the supported `dcs-build` primitives, `model/plant.json` and `model/dynamics.json` checked in, `deploy/manifest.json` recording the model fingerprint, `ci/check.sh` running resolve/build/byte-stable emit/released-tooling/fingerprint/scripted-simulation stages, and `crates/dcs-build/tests/reference_plant.rs` materializing the tree outside the workspace and running that check green against the `file://` stand-in. The tree's publication as a separate repository landed under #383.
3. Run clean cross-repository CI with no DCS source checkout present: compose deterministically, validate, lint, assemble-check, simulate, start the generic controller/UI, and verify the model fingerprint and declared operator surface. **Done** — `reference-plant/ci/check.sh` is that clean-CI pipeline: the `resolve`/`build`/`lockfile` stages compile the consumer against the pinned release with git-only lockfile sources (no path or DCS-source references), `emit` proves the byte-stable model, `tooling` runs released `dcs-model validate`/`lint` and `dcs-controller --check`, `fingerprint` and `deploy` verify the manifest against the emitted model (#389, served-dynamics authorization #842), `simulate` runs the scripted driven scenario, `surface` exercises the served operator surface (#366, extended to the served block-interface registry, declared commands, and emitted events under #384), and `consumers` proves the boundary schedules (#378). The workspace-side proof is `crates/dcs-build/tests/reference_plant.rs`, which materializes the tree outside the workspace and runs the same check green; #383 cut the `v0.1.0` release and published the tree as the independent repository (supervisor operations).
4. Prove one compatible platform upgrade by changing only the pinned DCS release and record a named failure for an incompatible API or model version. Publish a customer quick start that follows this exact path. **Done** — `crates/dcs-build/tests/consumer_upgrade.rs` (#352) replays a consumer's repin to a later compatible revision and names the incompatible crossings, and the reference plant's own `check.sh` `upgrade` stage exercises the documented repin inside its clean CI (#388), refusing an out-of-`MODEL_VERSION` document by name. `docs/customer-quickstart.md` (#351) publishes the quick start following exactly this path — create the repository from the `reference-plant/` tree, pin the release, compose and emit, validate, simulate, deploy through `deploy/manifest.json`, and upgrade by repinning.

Done — the separate reference-plant repository passes those checks from a clean checkout, its manifests contain no path into the DCS source tree, the generic image runs its mounted model without a customer-specific rebuild, and the platform repository's fixtures are described only as conformance tests rather than customer-project examples (`docs/model-reference.md` states that boundary outright; `docs/release-contract.md` names the conformance-fixture role).

## Foundation tranche (M12): schema-driven blocks and disposable UI — done

Requirements `WW-FND-003` and `WW-FND-004` plus decisions 82–83 made two QiTech-inspired ideas explicit implementation work, not optional UI polish. DCS copies the architectural separation, not the LGPL-3.0 implementation, its YAML format, or its session-shutdown policy. The `WW-ENG-003` cross-repository publication and clean-CI proof landed first (the M11 gate above); this tranche then executed ahead of broad new component kinds while already-active water slices and concrete reliability or field-hardware prerequisites finished alongside.

The tranche executed as ordered slices:

1. Define the additive, versioned `BlockInterface` contract in the shared layer and map the existing `ComponentDescriptor`, typed ports, parameter descriptors, signal metadata, writable points, and journal vocabulary into its five explicit collections: measurements, configuration, runtime state, named commands, and emitted events. Pin `dcs-build` specs, registry construction, runtime registration, and the served schema with one drift test. **Done (#363, #375)** — `dcs-core`'s `BlockInterface` (`crates/dcs-core/src/interface.rs`) carries the five collections at `INTERFACE_VERSION` 1, `BlockInterface::from_descriptor` is the single adaptation, `dcs-blocks/tests/spec_drift.rs` is the drift authority pinning every registered `KIND`'s spec, descriptor, derived interface, and served-schema document together, and `dcs-monitor` serves the instance-level form over `GET /schema` (the bound-point-annotated interfaces with the signal index's `unit`) and `GET /resources` (the same publication's live resource state) — the served document's emitted JSON Schema is `dcs-model interface-schema` (#394).
2. Add the missing behavior contracts: named commands with typed request data and capability/refusal metadata, settling through the existing bounded scan-boundary receipt path; typed emitted events with stable identities, payload schema, sequence, and declared retention. Do not turn commands into writable magic points or fire-and-forget messages. **Done (#374, #377, #381, #382)** — the descriptor's `commands`/`events` declare `CommandDecl`s (typed `CommandArgument` request, `CommandAvailability`) and `EventDecl`s (typed `EventField` payload, `EventRetention`); `Command::Invoke` validates a submission against the declaration and dispatches it at the scan boundary through the component's `invoke_command` hook, a refusal settling as `CommandRefused` on the ordinary receipted path; `drain_events` runs after every `step` — a failing step's emissions included — and journal-retained emissions land as `event_emitted` at the producing tick. `sequencer` proves both halves with `advance`/`reset` and `step_completed`; decision 84 (#381) pins the emit-identical standby semantics, the carried `Accepted`-invocation settling exactly once at promotion, and `Peer::final_sync`; #382 exercises the surface through the checked-in reference compositions.
3. Move monitoring reads onto immutable post-scan publications and bounded history/event storage outside the executor lock. Add sequence/freshness/gap reporting, bounded command admission with a named full-queue rejection, and overload metrics. No socket operation or consumer serialization may hold the executor across a scan. **Done (#364, #365, #376, #395)** — every read endpoint serves the bounded store's published copies, `Executor::with_command_queue_capacity` bounds ingress and answers overflow with the named `queue_full` receipt while admission metrics ride the snapshot's `command_queue` section and publication counters its `publication` section, `crates/dcs-monitor/tests/noninterference.rs` proves byte-identical authoritative artifacts across the failure matrix with named-gap and freshness coverage for bounded eviction, and #395 surfaces the publication gap and freshness state on the page.
4. Render the current reference plant from the served schema and live resource state with no kind-specific UI required for measurements, state, configuration, commands, or events. Custom presentation may enhance the generic result but cannot be required to operate a declared block. **Done (#379)** — `crates/dcs-monitor/src/page.html` joins `GET /schema` and `GET /resources` into a per-component disclosure rendering all five categories (labeled measurement/state readouts with unit and quality, configuration rows on the existing receipted `set_parameter` path, the availability- and refusal-aware command table with typed argument controls, and the component-attributed recent-events list), opened by default for kinds with no dedicated presentation; `dcs-ctl invoke` exercises declared commands through the served schema without a browser. `dcs-monitor/tests/interface.rs` pins the renderers and no-markup operability, `dcs-monitor/tests/ctl.rs` the applied/refused invocation receipts, and `dcs-build/tests/pump_station.rs` the served surface over both duty/standby documents — the platform fixture and the consumer tree's emitted `reference-plant/model/plant.json`.
5. Prove the boundary end to end from the external customer-shaped reference plant: identical deterministic outputs and command receipts with no UI, normal polling, a stalled reader, disconnect/reconnect, malformed/flooded traffic within declared limits, and a UI process restart. The controller remains active throughout; slow readers see coalescing or an explicit gap. **Done (#378)** — `reference-plant/ci/check.sh` gained the `consumers` stage: `ci/consumers.py` replays the scripted simulation's deterministic driven run once per consumer schedule (zero-clients, polling, stalled-reader, disconnect-reconnect, malformed-and-flood, ui-restart) asserting one identical `consumer-digest` over leg outcomes and command receipts across every schedule and across two passes, with named diagnostics `consumer-interference`/`consumer-nondeterministic` and a boundary lint pinning the stage's files to released artifacts and documented endpoints.

Done — every registered kind passes interface-schema drift coverage (`dcs-blocks/tests/spec_drift.rs`), the generic UI exposes all five resource categories for the reference plant (#379), command admission remains validated and receipted under overload (#365), and the non-interference proofs show UI delivery cannot pace or terminate plant execution (#376, #378).

### Seams the tranche left open

Recorded here so the record is complete; none blocks the next tranche.

- `EventRetention::History`/`Latest` emissions route to the bounded publication storage decision 83 owns (#458): `History` lands in the read model's bounded `EventRecord` event-history ring — evicting oldest-first at its declared bound under the same numbering-gap convention as the point-history and journal rings — and `Latest` stands in the latest-emission view, the newest record per (component, declared event) superseded by each newer emission. `GET /resources`'s per-instance `events` and `dcs-ctl events` serve both classes beside the retained journal tail under the existing attribution rule, each entry's `retention` mark telling the diagnostic streams from the durable record; `Journal`-retained and undeclared emissions journal `event_emitted` exactly once, and a tracking peer's published read model carries the same routed events (decision 84's emit-identical parity).
- `GET /resources` reports a `KindDeclared` command `available` unconditionally: the kind's availability predicate is evaluated only at dispatch, so the refusal reason surfaces through the settled `command_refused` receipt rather than the read model. **Closed (#457, #461)** — `Component::command_refusal` is the argument-free standing-availability probe (default reporting every declared command invocable), the executor evaluates it once per declared `KindDeclared` command at each scan's step end and publishes the verdicts in the snapshot's additive `command_verdicts` section, and `GET /resources`' `command_state` joins each published verdict into the served `CommandState` — `available: false` carrying the kind's named refusal where the probe refuses, a publication lacking the section keeping the earlier unconditional `available`. The verdicts stay advisory: the receipted path remains the sole authority, and a tracking standby re-derives identical verdicts from adopted state.
- The standby's event-emission semantics (emit-identical tracking, exactly-once carried invocations, `final_sync`) and the served endpoint shapes (`GET /schema` answering `SchemaView`, `GET /resources` answering `ResourceView`, `dcs-model interface-schema` emitting their JSON Schema) are recorded — decisions 84 and 82 respectively — rather than left open.
