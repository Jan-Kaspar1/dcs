# Water and wastewater requirements

This is the initial requirements baseline for the first target market. It is intentionally narrower than a complete water-industry DCS specification. The simulated reference plant is a duty/standby pumping station with a wet well or tank, level measurement, discharge measurement, motor feedback, permissives, trips, and operator controls.

Station operating-policy evidence and open assumptions are recorded in `docs/research/pumping-station.md` (issue #195); the requirement entries below cite it where the sources sharpen or qualify the acceptance evidence. Alarm-lifecycle evidence and the IJmuiden 2023 high-water near miss are recorded in `docs/research/alarm-management.md` (issue #234); the alarm contract is recorded as decisions 70–77 (issue #273). The QiTech framework's schema-separated resources and runtime/report boundary are recorded as a design reference in `docs/research/qitech-framework.md`; decisions 82–83 select the DCS behavior without adopting its code or complete runtime semantics. Filter backwash sequencing and shared-resource coordination evidence for `WW-CTL-004` is recorded in `docs/research/filter-backwash.md` (issue #233). Aeration and dissolved-oxygen control evidence for `WW-CTL-005` is recorded in `docs/research/aeration-do-control.md` (issue #241). Deployment, backup/restore, upgrade, and commissioning lifecycle evidence for the `WW-LCM-002` candidate is recorded in `docs/research/deployment-commissioning.md` (issue #242). Engineering-workflow evidence for the `WW-ENG-002` candidate — tag and naming conventions, I/O-list and loop-drawing deliverables, typicals and site-specific parameter sets, bulk editing and commissioning, and configuration-change review — is recorded in `docs/research/bulk-engineering.md` (issue #243). Identity, authorization, audit-retention, and security-zone evidence for the `WW-SEC-001` candidate is recorded in `docs/research/security-identity.md` (issue #255). Operating-report, regulatory-record, energy-metric, and maintenance-export evidence for the `WW-REP-001` candidate is recorded in `docs/research/operations-reporting.md` (issue #256). The open assumptions these entries record are consolidated into the per-phase pilot customer-acceptance checklist in `docs/research/pilot-acceptance.md` (issue #554) — which items are satisfied by landed product evidence, which need a first-client decision with a named owner, and which stay out of scope — without changing the statuses below.

## Accepted foundation requirements

### WW-FND-001 — One plant contract

- **Status:** accepted; substantially implemented
- **Need:** An engineer declares devices, signals, relationships, control components, and display metadata once. The controller and operator UI consume the same versioned model.
- **Acceptance evidence:** A checked-in reference model validates, assembles, runs in simulation, and supplies the metadata used by its monitoring UI without a second hand-maintained UI configuration.

### WW-FND-002 — Hardware-independent control

- **Status:** accepted; substantially implemented
- **Need:** Water library logic addresses typed logical I/O. A plant mapping selects simulation or a field-interface driver without changing component logic.
- **Acceptance evidence:** The reference application runs unchanged against at least two registered driver kinds, with mapping and type failures rejected before the first scan.

### WW-FND-003 — Schema-driven block interface

- **Status:** implemented — the versioned `BlockInterface` contract and its descriptor adaptation live in `dcs-core` (`BlockInterface::from_descriptor`, #363), pinned by the `dcs-blocks/tests/spec_drift.rs` drift sweep over every registered kind; named-command dispatch and kind-emitted events run through `Component::invoke_command`/`drain_events` (#374, #377) with the redundant-pair semantics decision 84 records (#381); `dcs-monitor` serves `GET /schema`/`GET /resources` from the published read model (#375) with `dcs-model interface-schema` emitting the served document's JSON Schema (#394); and the generic consumer is the page's per-component five-category surface plus `dcs-ctl invoke` (#379, #422), proven by `dcs-monitor/tests/interface.rs` (a kind with no dedicated markup fully operable), the invoke cases in `dcs-monitor/tests/ctl.rs`, and `dcs-build/tests/pump_station.rs` serving both the platform fixture and the consumer tree's emitted `reference-plant/model/plant.json` (#382, #384). The consumer-side half — the pinned `interface-schema` emission byte-pinned to the release record's artifact and the served `GET /schema` document checked against its required structure — runs in the reference plant's clean CI (#486).
- **Need:** Every reusable block type declares one typed, versioned, machine-readable interface that separates measurements, configuration properties, runtime state, named commands, and emitted events. Engineering tools, validation, simulation, monitoring, and UI consume this same declaration instead of maintaining kind-specific copies or inferring semantics from names.
- **Acceptance evidence:** Every registered block kind exports a serializable interface schema with stable resource identities, value or payload types, access direction, constraints, units/quality semantics where applicable, and command/event metadata. Assembly rejects an instance whose bindings or parameters do not satisfy the declared interface before the first scan. A generic consumer renders the reference plant's measurements and state, configuration editors, command affordances, and event stream without kind-specific UI code. The existing `ComponentDescriptor`, typed ports, `ParameterDescriptor`, signal index, receipted command path, and journal are migrated or adapted as one compatible contract rather than duplicated. Schema/version compatibility has named failures and a drift test pins engineering specs, runtime registration, and the served interface to one declaration.

### WW-FND-004 — Plant authority independent of UI delivery

- **Status:** implemented — the bounded publication and command-ingress halves are #364 and #365; the runtime-side matrix is `crates/dcs-monitor/tests/noninterference.rs` (#376: byte-identical authoritative artifacts across the failure matrix, named-gap and freshness coverage for bounded eviction), and the consumer-side end-to-end proof is the reference plant's `consumers` clean-CI stage (#378, `reference-plant/ci/consumers.py`): identical output and receipt digests across no-UI, polling, stalled-reader, churn, malformed/flood, and UI-restart schedules against released tooling only.
- **Need:** The controller backend owns authoritative plant execution and state. Monitoring pages, historians, and other UI consumers are disposable: absence, slowness, malformed traffic, disconnect, or restart cannot delay a scan, change an output, stop the plant, or become part of the controller's liveness decision.
- **Acceptance evidence:** A paced reference run produces identical ticks, outputs, checkpoints, and command outcomes with no UI, a normally polling UI, a stalled/disconnected reader, a reconnecting reader, and telemetry load at the declared bound. Read-side delivery consumes immutable published snapshots/events through bounded storage without holding the executor across socket I/O or consumer serialization; slow consumers observe coalescing or an explicit sequence gap/freshness state rather than backpressure on execution. Mutations use only a bounded validated command ingress, settle at the deterministic scan boundary, and return a receipt or a named admission rejection—commands are never fire-and-forget. The UI process can stop and restart while the controller remains active, and a transport failure is reported as consumer/monitoring health rather than a plant shutdown condition.

### WW-OPS-001 — Consistent equipment operation

- **Status:** accepted
- **Need:** An operator can understand and control common equipment through consistent modes, status, commands, permissives, interlocks, trips, feedback discrepancy, and unavailable states.
- **Acceptance evidence:** The reference pumping station demonstrates these states end to end for its pumps and valves, including descriptor-driven faceplates and receipted commands. Per `docs/research/pumping-station.md`, evidence supports: per-pump mode selection (automatic, manual, and an out-of-service/maintenance inhibit), permissive gating of starts, interlock trips, failed-feedback flags after a declared delay, and an aggregated "available" state per pump. The full vendor-style mode vocabulary (program, override, maintenance, hand) is an open assumption pending customer validation — the reference station needs only the modes its operator workflow uses.

### WW-OPS-002 — Alarm and event handling

- **Status:** accepted
- **Need:** Abnormal process and equipment conditions are visible with lifecycle state, timestamps, acknowledgment, and actor attribution sufficient for an operator to understand what happened.
- **Acceptance evidence:** The reference application generates representative process and equipment alarms, exposes current alarm state and transition history, and preserves the durable journal across a controller restart. The representative set includes high and low wet-well level, per-pump fail-to-start and fail-to-stop, measurement fault, backup-control-mode engagement, and station power/communication faults — each a latching alarm with a standing flag, an unacknowledged latch, and a journaled acknowledgment. `WW-ALM-001`–`WW-ALM-005` extend this base with priority and rationalization data, managed states, consequential annunciation, flood performance, and the protection boundary; which alarms latch and the site's priority vocabulary remain customer-configured policy.

### WW-OPS-003 — Signal and communication confidence

- **Status:** accepted; partially implemented
- **Need:** Operators and control components can distinguish healthy, uncertain, bad, stale, and deliberately substituted data, and can see field-communication and scan-health problems separately from process alarms.
- **Acceptance evidence:** Simulated sensor faults, link loss, and forces propagate through control behavior, telemetry, diagnostics, and UI with deterministic recovery behavior. Station-facing sharpening from the research note: level measurement uses redundant sources with a declared failover — a bad or lost primary measurement switches the station to a declared backup (secondary transmitter or float-backup mode) and raises an alarmed transition rather than silently controlling on bad data. The single-primary-plus-float-backup versus multi-transmitter master-selection choice is a customer-validation question.

### WW-CTL-001 — Pump duty management

- **Status:** accepted
- **Need:** An engineer can compose a pump group that selects duty and standby pumps, rotates duty by declared policy, starts additional capacity on demand, respects availability and permissives, and handles a running pump failure.
- **Acceptance evidence:** A deterministic simulation covers normal alternation, unavailable duty pump, failed start or run feedback, assist demand, and return to normal capacity. Evidence-supported specifics from the research note: the rotation policy is a declared choice — alternate each cycle, alternate on a timed interval, or least-run-hours first — because owner policies demonstrably differ; a lag pump stages at its own start level when the duty pump cannot hold the level; a failed or unavailable duty pump hands duty to the standby; start/stop sequences respect a declared inter-pump start delay and engineered starts-per-hour limits. Open assumptions to validate: the first client's default rotation policy, whether failure hands over automatically or alarms-and-waits, and whether a failed pump latches out until reset.

### WW-CTL-002 — Level-based station control

- **Status:** accepted
- **Need:** The reference station controls level using declared start and stop thresholds or a continuous controller, with explicit behavior for bad level measurement and manual operation.
- **Acceptance evidence:** Scenarios cover normal inflow, high and low levels, changing inflow, bad measurement, manual takeover, and recovery without an unintended output step. Evidence-supported specifics from the research note: the threshold form is an ordered setpoint chain — low cut-off, duty start/stop, lag start, high-level alarm — with operator-adjustable setpoints; the continuous form is constant-level control for variable-speed stations with a minimum-speed cycling bound; a bad primary measurement fails over to a declared backup mode or voted source with an alarmed transition; manual takeover is a per-pump mode that persists declared protections (e.g., motor over-temperature) while the operator holds the demand. Open assumptions to validate: which control form is primary for the first client, behavior when all level sources are bad, and which protections persist in manual.

### WW-CTL-003 — Chemical dosing and flow-paced control

- **Status:** accepted
- **Need:** An engineer can compose a dosing function that paces a metering pump to a measured process flow at an operator-set dose, bounds the demand within declared dose and rate limits, respects declared permissives and interlocks, accounts for chemical consumed, and responds predictably to a lost pacing signal or a proven pump fault.
- **Acceptance evidence:** A simulated dosing loop demonstrates: flow-paced ratio control delivering the declared dose per flow unit across the flow range; the demand clamped at declared minimum and maximum dose and pump-rate limits with a clamped indication; dosing inhibited until declared permissives hold (process flow proven, metering pump available, chemical tank above the low level) and dropped to the safe value on loss of any permissive; the declared response to a bad pacing-flow signal — stop, hold, or fallback rate — taken with an alarmed transition; consumption totalized from the commanded or measured chemical rate; and the declared skid alarm set raised. Evidence-supported specifics from `docs/research/chemical-dosing.md`: flow-paced ratio control is the primary mode owner specifications require — dose per flow unit (e.g., mg/L) times measured flow — with fixed-rate as a declared alternative for steady-flow service and diurnal profile dosing a specified third form, deferred until a customer names it; feedback trim by a residual or quality analyzer is an optional compound layer over pacing; actuation is a speed demand or an on/off run command, with stroke length an engineering/operator setting rather than a control output; loss of any dosing permissive stops the pump and inhibits restart; a proven no-discharge or pump fault alarms and can hand over to a standby pump. The dosing contract is recorded as decisions 50–55: the `flow-paced-ratio` kind — `flow`/`dose`/optional `trim` in, bounded `demand` plus `clamped` and `fallback_active` out, the dose setpoint on a writable internal point, and the declared `on_bad_flow`/`on_bad_trim` responses (decision 50); the permissive chain composed from `interlock`/`bool-gate`/`sr-latch`/`sequencer` wiring, demand dropping to the declared safe value on loss and restart inhibited until permissives return (decision 51); the `motor` + `analog-output` actuation composition with stroke length an engineering setting (decision 52); commanded totalization plus the `deviation-monitor` expected-versus-measured check where a measured-consumption signal exists (decision 53); the diurnal-profile deferral and its revisit condition (decision 54); and the skid alarm set on the two-flag lifecycle (decision 55). Open assumptions to validate: the first client's primary control mode; the default `on_bad_flow` response and whether it must be operator-selectable; whether a clamped demand alarms or only flags; the per-pump actuation contract (speed-only, speed-plus-stroke-servo, or run-only) and whether pulse-per-stroke pacing is an input form; which alarms latch until acknowledged; the manual-takeover scope and which permissives persist in manual; whether analyzer trim is in scope; whether dose confirmation requires a measured-consumption signal; and whether chemical-tank inventory management belongs to the dosing contract or a separate tank component.

### WW-CTL-004 — Filter sequencing and backwash coordination

- **Status:** accepted
- **Need:** An engineer can compose a bank of N granular-media filters, each stepping through a declared backwash sequence against a shared air/water backwash supply that serves one filter at a time, with declared trigger sources, per-step advance conditions, exclusive-grant arbitration among contending filters, declared mid-sequence failure behavior, operator intervention, and a declared alarm set.
- **Acceptance evidence:** A deterministic filter-bank simulation demonstrates: a backwash request raised by each declared trigger — elapsed filter run time, terminal headloss, effluent turbidity above its bound, and operator start — with the firing trigger recorded per backwash; the declared step sequence advancing on time and on measured state per the step declaration (drain-down ending on level reached, wash phases on declared durations, filter-to-waste ending on a turbidity and/or volume bound); each step driving its declared valve/pump/blower pattern subject to phase-internal guards (e.g., no simultaneous air scour and high-rate wash); at most one filter in backwash at a time, contending requests ordered by the declared queue policy with the grant conditional on declared capacity permissives (washwater supply available, waste capacity, online-flow disturbance bound) and released on completion or abort; a queued filter in its declared meanwhile state (keep filtering until granted, or offline with standby cover); operator start, abort, and queue reorder through the receipted command path; a proven equipment fault mid-sequence driving the filter to its declared on-fault step and raising an aborted status distinct from complete; and the declared alarm set raised (per-filter effluent turbidity tiers, terminal headloss, aborted/failed backwash, resource-blocked queue, post-wash clean-bed-headloss and ripening excursions). Evidence-supported specifics from `docs/research/filter-backwash.md`: the canonical sequence is timed cleaning phases bounded by measured-state steps (drain-to-level, filter-to-waste-to-turbidity/volume) with an operator-adjustable resting period; the trigger set — run time, headloss, effluent turbidity, operator start — is owner-convergent while whether automatic triggers may *start* a wash versus only queue a request is jurisdiction-specific (both directions are mandated in different rules), so auto-start permission is itself declared; an ordered backwash queue with one-at-a-time execution and operator reorder is owner-evidenced (FIFO default); operator abort and override are required vocabulary. The filter-bank contract is recorded as decisions 56–61: the `backwash-coordinator` kind carrying the exclusive supply grant — per-filter `request_i`/`grant_i`/`position_i` ports under the indexed convention, `active`/`queued`/`resource_blocked` status outputs, a declared `queue_policy`, the declared `supply_ok`/`waste_ok`/`flow_ok` grant permissives, release on completion or abort through the request drop, the declared `queued_state` meanwhile behavior, and operator queue reorder through the receipted path — plus a `dcs-build` builder-level bank-composition helper (decision 56); the `backwash-sequence` kind — per-step advance on ticks and/or a declared measured bound with declared overrun behavior, generated `phase_<n>` outputs whose `bool-gate` decode drives the plant's equipment pattern under the declared phase guards, and grant-gated start with `request` drop releasing the grant (decision 57); the declared four-source trigger set with the `auto_start` permission as declared data and journaled `trigger_source` attribution (decision 58); the operator surface — start, abort-to-the-declared-safe-step, queue reorder, and per-step tuning through the receipted command path, with hold/advance/manual-step recorded as open (decision 59); the declared `on_fault` step and `on_fault_policy` with `aborted` distinct from `done` (decision 60); and the `phase-monitor` checks plus the bank alarm set on the decision-38/43 two-flag lifecycle (decision 61). Open assumptions to validate: whether automatic triggers may start a wash for the first client or only queue a request for operator start; the queue discipline and reorder authority; the queued filter's meanwhile state and the grant permissives the client's hydraulics require; the on-fault step and resume-versus-abort policy, and whether an aborted filter returns to service without a completed wash; whether hold/advance/manual-step commands are required operator surface; the client's step vocabulary and which step ends are measured versus timed; and which alarms latch until acknowledged, including the 1 NTU tier's alarm-versus-trip scope.

### WW-CTL-005 — Aeration and dissolved-oxygen control

- **Status:** accepted
- **Need:** An engineer can compose a diffused-air aeration train that holds dissolved oxygen at an operator-set value in each controlled zone, coordinates the blowers against a shared air header so the demanded airflow is delivered within declared pressure bounds, stages and protects the machines, responds predictably to a lost DO measurement, accounts for the air delivered, raises a declared alarm set, and admits manual takeover at each layer.
- **Acceptance evidence:** A deterministic aeration-train simulation demonstrates: constant-DO feedback per zone, with the declared cascade form where the DO loop's output is the airflow loop's set-point; shared-header coordination by the declared strategy — constant header pressure, most-open-valve pressure reset keeping one zone valve at a declared near-open position, or direct-airflow control — within declared header-pressure bounds; blower staging that starts and stops machines on demand under declared minimum-run-time and start-interval bounds, excludes unavailable or faulted machines, and hands demand to a standby; declared machine protections — the surge/minimum-flow guard, high header pressure, bearing and motor faults — outranking the demand and driving the machine to its safe state with a reasoned alarm; the per-zone minimum-mixing airflow floor enforced regardless of DO demand; the declared response to a non-good DO measurement — a voted or backup-selected measurement first, then a declared fallback (hold last demand, fixed airflow, or declared safe airflow) with an alarmed transition; airflow measured per zone and totalized at the header; the declared alarm set raised; and operator takeover of each demand through the receipted command path with the machine protections persisting. Evidence-supported specifics from `docs/research/aeration-do-control.md`: constant-DO feedback with a DO-to-airflow cascade is the owner-specified baseline, with header-pressure control as the alternative outer loop and the DO set-point optionally reset by an ammonia-based supervisory loop or load feed-forward; actuation combines per-zone modulating air valves with blower capacity by speed, inlet-guide-vane or inlet throttling, or on/off staging as the machine type dictates; shared-header coordination needs a declared strategy because independent zone loops hunt through the common header — constant pressure, most-open-valve pressure reset, and direct-airflow control are all evidenced; surge protection, the machine protective trip set, and the minimum-mixing floor are bounds the demand must respect; DO measurement redundancy takes probe-select, averaging, or voting forms, while the terminal fallback on total DO loss is not uniformly specified and must be declared. The aeration contract is recorded as decisions 62–69: the `header-coordinator` kind — per-zone `valve_pos_i`/`airflow_i`/`pulsing_i` inputs plus the header `pressure`, `pressure_sp`/`blower_demand`/`pulse_grant_i` outputs, the `most_open`/`at_bound`/`pulse_blocked` status outputs, the declared `strategy` (constant header pressure, most-open-valve pressure reset inside the declared band, or direct-airflow control), the declared pressure bounds, and the `max_pulsing` mixing-pulse cap — plus a `dcs-build` builder-level train helper (decision 62); the `blower-group` kind — the Float `demand` split across running units, per-unit `cmd_i`/`run_i`/`fault_i`/`avail_i`/`capacity_i`/`vent_i` ports, declared stage-up/down thresholds and minimum-run and start-interval bounds, the declared `staging_authority` and `rotation`, and the start-offline-through-vent join choreography with the `transition` surface for the valve-freeze rotation handover (decision 63); the `surge-guard` kind — the two-variable flow-versus-pressure demand guard with the hardwired protective set reporting status only (decision 64); the `demand-fallback` kind carrying the declared `on_bad` response on the DO-to-airflow demand path with the alarmed `fallback_active` (decision 65); the additive `feedforward-sum` kind beside the landed multiplicative `flow-paced-ratio`, with ammonia-based supervision composing as set-point wiring (decision 66); the `motor` + `analog-output` blower composition with mechanical aerators recorded outside the contract's scope (decision 67); measured-and-totalized airflow in-contract with derived energy metrics deferred to `WW-REP-001` (decision 68); and the alarm set mapped onto the decision-38/43 two-flag lifecycle as wired `latching-alarm`/`bool-latching-alarm` instances (decision 69). Open assumptions to validate: the first client's primary mode and whether ammonia-based supervision or load feed-forward is in scope; the header `strategy` and its declared bounds including the most-open-valve band; the all-DO-bad `on_bad` response and whether it is operator-selectable; the per-zone measurement architecture (single, primary/backup, averaging, or three-probe voting) and whether discrepancy flags alarm; the staging authority, rotation policy, and per-unit bounds; the per-blower actuation form and whether any machine couples the composition halves in a way that reopens a `blower` kind; the required alarm set and latch policy, including the comm-fail and staging-pending questions; whether derived energy and specific-power metrics stay deferred to `WW-REP-001`; whether mechanical aerators are in scope for the first client; and whether the mixing-pulse coordination is required or specific to pulsed-aeration designs.

### WW-ALM-001 — Rationalized alarm contract and priority

- **Status:** accepted
- **Need:** Every configured alarm identifies an abnormal condition that requires operator action and carries the information needed to act: stable identity and source, priority, class, condition and lifecycle state, source and receive timestamps, process value and limit where applicable, signal quality, operating mode, consequence of inaction, required action, allowable response time, and a link or reference to the relevant display or procedure.
- **Acceptance evidence:** The reference application declares this rationalization data once and the controller, alarm summary, equipment faceplate, history, and engineering validation consume it consistently. Validation rejects an alarm without a required response or priority basis. Acknowledgment records operator awareness without clearing or hiding an active condition, and every activation, return, and acknowledgment remains ordered and attributable across restart. The rationalization carriage is recorded as decisions 70 and 74: identity lands as the component instance plus the `Signal` naming its standing point; `priority`, `class`, and `response_ticks` are descriptor-declared parameters on the alarm kinds served live through the snapshot's parameter section; the prose record — consequence of inaction, required action, and the display/procedure reference — is an optional `rationalization` block on the component instance under the version-1 optional-field convention; and the required-response/priority-basis rejection lands where kind identity is known — alarm-kind construction at assembly and `dcs-controller --check`, with `dcs-build`'s alarm specs taking the fields as required typed arguments (decision 70). Activation, return, and acknowledgment order across restart rides the declared `journaled` point flag and the generic `PointChanged` journal event beside the attributed settled receipts (decision 74). Open assumptions to validate: the site priority vocabulary — level count, names, and colour/indication conventions — plus the class rules and highly-managed membership; which alarms latch until acknowledged; the per-alarm response-time values; and whether priority must ever be state-driven.

### WW-ALM-002 — Managed alarm lifecycle

- **Status:** accepted; substantially implemented
- **Need:** Operators can distinguish active, acknowledged, returned-unacknowledged, shelved, suppressed-by-design, and out-of-service alarms. Temporary shelving is bounded and attributable; designed suppression follows declared plant state; out-of-service handling follows a separate maintenance path. No managed state erases alarm history.
- **Acceptance evidence:** A deterministic scenario demonstrates actor-and-reason-attributed shelving with a per-alarm maximum and automatic expiry, manual unshelving, visible designed suppression and its cause, and a manual out-of-service/return-to-service path. Non-shelvable critical alarms reject shelving. The alarm summary exposes each managed list and still shows counts when annunciation is suppressed. The managed-lifecycle contract is recorded as decisions 71–74: the three managed states are the uniform `shelved`/`suppressed`/`out_of_service` status-port vocabulary the summary pane renders as managed-state lists across kinds, with a first-class served field deferred to a named revisit (decision 71); shelving and out-of-service land as the managed sibling kinds `managed-latching-alarm`/`managed-bool-latching-alarm` — level-observed `shelve`/`oos` writable points on the receipted, actor-attributed path, a declared `max_shelve_ticks` with automatic expiry, non-shelvable rejection through the unbound or unwritable point and the zero bound, and manual-only return from out-of-service (decision 72); designed and state-based suppression stays declared wiring, landing on the `suppress` input so the kind asserts the named `suppressed` state rather than silently gating `in` (decision 73); and the lifecycle audit is the attributed receipts plus decision 74's journaled transitions — a narrowed, explicitly recorded reopen of decision 33's journal-event rejection that adds one generic declared-point transition event while dedicated alarm event types stay rejected. Open assumptions to validate: which alarms may be shelved and their maximum shelve times; whether the operator chooses the shelve period within the bound; shelving authority — who may shelve — and how the shelving reason is captured; the shift-review workflow; the suppression policy — which alarms are state-dependent; and whether out-of-service is the client's expected alarm state or the equipment maintenance-inhibit mode covers the intent.

### WW-ALM-003 — Consequential state and process annunciation

- **Status:** accepted
- **Need:** A mode or authority change, command/confirmed-position mismatch, worsening high-consequence process condition, or bad/stale measurement cannot remain hidden in separate screens or appear as a healthy last-known value. New actionable alarms use redundant visual coding and site-policy-driven audible annunciation, remain visible while active, and give the operator the related equipment state, trend, quality, and control mode.
- **Acceptance evidence:** A reference scenario patterned after the 2 November 2023 IJmuiden near miss switches water-control equipment from automatic to manual, leaves its confirmed state inconsistent with the safe demand, and drives a rising level. The operator surface raises and relates the mode change, position discrepancy, rate-of-rise/high-level condition, and any bad/stale data with priority and first-out timing; acknowledgment silences the annunciation without hiding the hazard. Tests also cover communication loss, frozen input, timestamp freshness expiry, navigation/filtering, and recovery. The consequential-annunciation surface is recorded as decisions 74 and 75, with priority from decision 70: the mode change annunciates through `bool-latching-alarm` on the mode/authority status and journals through the declared `journaled` point; the confirmed-state/demand discrepancy rides `valve`/`motor`'s `discrepancy`/`fault` flags; the worsening level rides `latching-alarm`/`threshold-chain`; bad or stale data presents degraded through the quality and declared-freshness seams, never as healthy last-known; priority renders with redundant colour-plus-text coding from the declared `priority` parameter; first-out order comes from the durable ordered transition record; and acknowledgment silences the annunciation demand while the hazard stands — the scenario becoming the scripted vertical acceptance case (decision 75). Open assumptions to validate: the site priority names, colours, and audible-annunciation policy; the delivery and escalation expectations for the unattended station — destination, call-out, re-alarming; and whether a discrete communication-failure alarm is required beyond the I/O-health surface.

### WW-ALM-004 — Alarm flood and performance management

- **Status:** accepted
- **Need:** The alarm system helps operators find the initiating cause during a burst and gives engineers evidence to remove nuisance alarms. State-based suppression or grouping may reduce consequential annunciation while preserving the original event sequence and suppressed counts.
- **Acceptance evidence:** Durable alarm data produces deterministic metrics for alarm and peak rate, flood periods, standing and stale alarms, chattering/fleeting alarms, most-frequent alarms, shelving duration, suppression state, and acknowledgment/response time. A simulated equipment trip proves first-out visibility and preserves every underlying transition while its consequential alarm burst remains manageable. The flood and performance surface is recorded as decision 76: the metrics compute over the durable journal and point history — which decision 74's declared journaled transitions supply across restart — with aggregation staying page-side per the decision-37 precedent; the flood thresholds and conventional performance targets are declared report configuration; and engineered flood suppression composes through decision 73's `suppress` wiring keyed on the trip state while the preserved ordered record keeps every underlying transition visible and countable. Open assumptions to validate: which metrics are acceptance evidence — alarm and peak rate, flood periods, standing and stale counts, chattering and most-frequent rankings, shelving duration, acknowledgment and response time; the site's flood thresholds versus the conventional 10-per-10-minutes bound; whether engineered flood suppression is required; and whether metrics must ever be served contract data rather than computed presentation.

### WW-ALM-005 — High-consequence protection boundary

- **Status:** accepted
- **Need:** Alarm handling is not credited as automatic protection where a water hazard requires an independent protective response. The DCS exposes the availability, activation, fault, bypass, trip, and proof-test state of such a protection layer without silently treating the ordinary HMI alarm path as the protection function.
- **Acceptance evidence:** The reference scenario declares the boundary between normal control, operator alarm response, and a simulated independent high-high protective action. Loss, bypass, or failure of the protection path is visible and audited; a hazard-analysis decision is required before any alarm-and-operator response is credited as a safeguard. The protection boundary is recorded as decision 77: the independent layer's availability, activation, fault, bypass, trip, and proof-test states are declared field points — annunciated through the two-flag kinds where required, journaled through decision 74's declared transitions, and presented distinctly under a declared signal group — while the protective function itself stays outside the DCS contract, simulated plant-side in the reference scenario, so the HMI alarm path is never credited as the safeguard. Open assumptions to validate: the hazard-analysis boundary — which functions require the independent layer — and whether that classification must land as declared model data; and the bypass authority and proof-test workflow expectations.

### WW-ENG-001 — Reusable plant composition

- **Status:** accepted; partially implemented
- **Need:** An engineer composes a plant from typed reusable components and receives validation errors for missing parameters, incompatible ports, invalid mappings, and incomplete operator metadata before deployment.
