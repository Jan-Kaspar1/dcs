# Architecture decisions

## Bootstrap baseline

The repository begins as a Rust workspace with a `dcs-core` library reserved for shared contracts. No controller or plant-model API has been chosen yet. Python standard-library tooling coordinates development; it is not the plant runtime.

The project vision in `AGENTS.md` is the source for product decisions. All initial I/O is simulated, and development excludes physical plant equipment and live deployment.

## Recording decisions

When choosing a shared contract, module boundary, persistence format, or runtime behavior, the planner records the problem, chosen approach, alternatives, consequences, and affected tickets here. Changes are committed and pass the same CI gate as implementation. Accepted decisions must distinguish implemented behavior from proposed behavior.

## Decisions

### 1. Workspace crate layout

- **Status:** Accepted and implemented: `dcs-core`, `dcs-model`, `dcs-runtime`, `dcs-sim`, and `dcs-blocks` all exist, joined by `dcs-monitor` (decision 8's transport, #20), `dcs-demo` (the M1 example loop, #12), `dcs-sim-net` (the remote simulated driver and shared plant server, #31 and #68), `dcs-assembly` (decision 6's model-driven wiring, #19, and the device-kind driver registry, #47), `dcs-controller` (decision 9's paced binary with active/standby modes, #19, #48, and #32), and `dcs-plant` (the standalone shared-plant server, #81).
- **Problem:** The system needs crate boundaries so that shared contracts, the plant model, the executor, simulated I/O, and reusable control components can evolve independently with an explicit dependency direction, instead of growing as one tangled crate.
- **Chosen approach:** One Cargo workspace. `dcs-core` holds shared contracts (signal types, quality, component and I/O traits). Planned members: `dcs-model` (plant model types and serialization), `dcs-runtime` (cyclic executor and component model), `dcs-sim` (simulated I/O backend), and `dcs-blocks` (reusable control components). Dependencies point inward: `dcs-model`, `dcs-runtime`, `dcs-sim`, and `dcs-blocks` may depend on `dcs-core`; `dcs-core` depends on none of them.
- **Alternatives considered:** A single monolithic crate (simpler, but couples contract stability to every feature); one crate per device or per component (fragments the workspace and multiplies publishing/versioning overhead).
- **Consequences:** Shared contracts change in one place and downstream crates break visibly at compile time. Each planned crate must be added as a workspace member before use. Component and test code can depend only on the layers it needs, keeping builds incremental.
- **Affected tickets:** #4 (this record); the planned M1 tickets that create `dcs-model`, `dcs-runtime`, `dcs-sim`, and `dcs-blocks`.

### 2. Signal representation

- **Status:** Accepted and implemented in `dcs-core` (issue #5): `Sample { value: Value, quality: Quality, tick: Tick }` with `Value` = `Bool`/`Int`/`Float`, `Quality` = `Good`/`Uncertain`/`Bad` carrying a `QualityReason`, and `Tick` a logical `u64` counter.
- **Problem:** Control logic and the monitoring UI need one uniform way to represent a process value that may be good, bad, stale, or substituted, and to know when it was sampled — bare scalars cannot express this.
- **Chosen approach:** A signal is a typed value plus a quality flag plus a timestamp: conceptually `Signal<T> { value: T, quality: Quality, timestamp: Tick }`, defined in `dcs-core`. `Quality` starts as a small enum (good, bad, uncertain/substituted) and may grow. The timestamp is a virtual tick count (see decision 4), not wall-clock time.
- **Alternatives considered:** Bare typed values with no quality (loses diagnostics the vision requires); OPC UA-style status codes and source/server timestamps (broad but heavyweight for a first contract); bespoke per-signal structs (no uniform handling in the executor or UI).
- **Consequences:** Every logical I/O point carries quality, so components must define behavior for non-good inputs and the executor can propagate bad quality to outputs. Timestamps are comparable only within a run's tick domain, which keeps tests deterministic.
- **Affected tickets:** #4; the M1 ticket implementing `dcs-core` signal contracts, and every later component and driver ticket.

### 3. Plant model serialization format

- **Status:** Accepted and implemented in `dcs-model` (#7): JSON documents carry a top-level `version` accepted only as `MODEL_VERSION` (currently 1), validation follows parsing, and optional fields extend the schema without a version bump (`Signal::unit`, `Signal::description`, `Signal::group` — display metadata grouping a signal under a plant area or unit for the monitoring page, #86). The derived `SignalIndex` (#23) and the `dcs-model` CLI (#36) build on it.
- **Problem:** The plant model is the single contract shared by engineering data, controllers, and the monitoring UI. It needs a serde-based on-disk format that is versioned, diffable, and readable by tooling outside the Rust workspace.
- **Chosen approach:** JSON via `serde`/`serde_json`. Every document carries an explicit top-level `version` field; the loader accepts only known versions and migration happens on load. The plant model is treated as an engineered artifact, typically produced and consumed by tools rather than hand-edited.
- **Alternatives considered:** TOML — friendly for hand-editing and comments, but awkward for the deeply nested device/signal/mapping lists the model needs and less natural for a web-based monitoring UI. RON — Rust-native with comments, but essentially no non-Rust tooling, which undermines the model's role as a cross-language contract.
- **Consequences:** Any tool that can parse JSON can read or generate the model, including the future monitoring UI. Lack of comments means explanatory text lives in model fields, not alongside the data. All model documents must state a version, so schema changes are explicit rather than silently ambiguous.
- **Affected tickets:** #4; the M1 ticket implementing `dcs-model`, and every later ticket that loads or emits plant configuration.

### 4. Execution model

- **Status:** Accepted and implemented in `dcs-runtime` (#9): `Executor::scan` advances a virtual `Tick` and runs apply-commands → read inputs → step components → write outputs in order; nothing reads a wall clock.
- **Problem:** The controller must execute reproducibly: the same plant model and input sequence must produce the same outputs on any host, and tests must be able to step through runs without real-time waits.
- **Chosen approach:** A deterministic fixed-step scan. Each cycle reads all inputs, steps components in a defined order, then writes all outputs. Time is a virtual tick counter advanced by the executor; components never read a wall clock. Pacing a run to real time, when needed, is the outer driver's concern, not the components'.
- **Alternatives considered:** Event-driven or `async`-task execution (flexible but ordering and reproducibility become scheduling-dependent); wall-clock timers inside components (nondeterministic, untestable); variable-step execution (breaks fixed-scan assumptions familiar from PLC runtimes).
- **Consequences:** Runs are deterministic and replayable; `dcs-sim` and tests can advance the executor one tick at a time. Components must express delays and periods in ticks. Real-time jitter is isolated to the pacing layer and cannot leak into control logic.
- **Affected tickets:** #4; the M1 ticket implementing `dcs-runtime`, and all component and simulation tickets.

### 5. I/O abstraction

- **Status:** Accepted. The contract side is implemented in `dcs-core` (issue #6): `IoDriver` provides untyped `read`/`write` over `PointId` returning `Result<_, IoError>` (unknown point, disconnected, timeout, type mismatch — each carrying the point identity), and `Input<T>`/`Output<T>` handles give components typed logical I/O with strict, never-coercing value matching. `SimDriver` implements the contract (#8); the TCP remote driver in `dcs-sim-net` implements it too (#31, decision 13).
- **Problem:** Per `AGENTS.md`, control logic must be hardware-independent: the same component must work whether a point is backed by local I/O, EtherCAT, Ethernet, or simulation, without code changes.
- **Chosen approach:** Components declare typed logical I/O points — a name, a signal type (decision 2), and a direction. Binding a logical point to a physical device channel lives in the plant model (decision 3); resolving that binding and talking to field hardware lives in drivers beneath `dcs-runtime`. Component code never names a device, bus, or address.
- **Alternatives considered:** Injecting driver handles into components (couples logic to a driver API); per-component mapping config (duplicates mapping outside the plant model, breaking the single-contract goal); a global string-keyed I/O registry (loses compile-time typing).
- **Consequences:** Components are portable and fully testable against `dcs-sim`. Rewiring hardware is a plant-model edit, not a code change. Mapping errors surface at model load or driver initialization rather than mid-scan.
- **Affected tickets:** #4; the M1 tickets implementing `dcs-core` I/O traits, `dcs-model` mapping, `dcs-runtime` drivers, and `dcs-sim`.

### 6. Model-driven assembly

- **Status:** Accepted and implemented (#19): `dcs-assembly` resolves a validated `PlantModel` into a `ChannelMap`, a `PointMap`, and per-instance port bindings — synthesizing internal point pairs for port-to-port links — and `assemble` constructs every component through an explicit `ComponentRegistry` keyed on `kind`, with unknown kinds, unbound ports, and mapping mismatches failing before any scan. `dcs-demo` retains its own fixed-registry assembly as the M1 example (#12). The device-kind factory registry is implemented (#47): `DriverRegistry::standard` resolves the `sim*` prefix to local simulated channels and the exact `sim-tcp` kind to `RemoteDriver`, `resolve_drivers` builds each declared device through its kind's factory, and `DriverPlan::build` finishes the driver side as a `FanoutDriver` presenting one `IoDriver` surface over the backends.
- **Problem:** The plant model declares component instances by opaque `kind` string plus parameters and port wiring, while the executor takes constructed components and a resolved point map. Something must turn a validated model into a configured driver and executor — and that translation has to live in a crate whose dependency direction respects decision 1.
- **Chosen approach:** A new workspace crate `dcs-assembly`, depending on `dcs-core`, `dcs-model`, `dcs-runtime`, and `dcs-sim`. It provides a component registry mapping each `ComponentInstance.kind` string to a constructor that receives the instance's parameters and resolved port-to-point bindings and returns `Box<dyn Component>`; reusable components from `dcs-blocks` register their kinds there. A builder takes a validated `PlantModel`, resolves devices into a driver-side `ChannelMap` and `SimDriver`, resolves `io_points` into the executor's `PointMap` (synthesizing internal points for port-to-port connections), constructs each component through the registry, and returns the configured executor and driver. Registration is explicit: an unknown kind is a build error naming the component instance, raised before any scan runs.
- **Alternatives considered:** Construction inside `dcs-runtime` (couples the deterministic executor to the model schema); inside `dcs-model` (inverts the dependency direction — the serialization contract would depend on the runtime); global self-registration via link-time tricks like `inventory`/`linkme` (component kinds silently missing when a translation unit is not linked); assembly code in each binary (duplicates the model-to-runtime logic across binaries and tests).
- **Consequences:** Adding a device or component kind means registering a constructor — instantiation, wiring checks, and diagnostics come from the shared layers instead of per-layer engineering. Model instantiation errors surface at build time, before the first scan. `dcs-model` stays serialization-only and `dcs-runtime` stays model-agnostic, so both remain independently testable.
- **Affected tickets:** #18 (this record); the M2 tickets creating `dcs-assembly`, the component registry, and `dcs-blocks` components that register with it.

### 7. Operator command path

- **Status:** Accepted and implemented (#20): `Command`/`CommandReceipt`/`CommandOutcome`/`CommandError` live in `dcs-core`; `Executor::submit_command` validates against the point map and queues, the scan head applies queued commands before the input read, and the receipt log is readable via `Executor::receipts`. Commands target `PointId`s (`Command::WriteValue`, plus the `ForcePoint`/`UnforcePoint` pair #84 adds under decision 21) and component instances (`Command::SetParameter`, #82, decision 20); writable targets are model-declared under #49 (decision 18).
- **Problem:** The monitoring and control UI must change a run's behavior — setpoints, mode switches, manual output overrides — through the same unified contract, and every attempted change needs an explicit accept/reject answer. The deterministic scan must define exactly when a command takes effect, or command ordering becomes timing-dependent and runs stop being reproducible.
- **Chosen approach:** A serde `Command`/`Receipt` pair defined in `dcs-core`, beside `TelemetrySnapshot`, so any transport or UI needs only the shared contracts. A `Command` names its target (a component instance or a point), an operation, and parameters. Commands are applied at one documented point: at the scan boundary, before the input-read phase of the next scan — never mid-step — so a queued command's effect begins at a known tick and the read → step → write order is preserved. Every command produces exactly one `Receipt`: accepted, reporting the tick it applied at; or rejected with a structured reason (unknown target, invalid or mistyped value, operation not permitted in the current state). Rejections are also visible through telemetry diagnostics so the UI can display them.
- **Alternatives considered:** Applying commands the moment they arrive, mid-scan (nondeterministic — the effect depends on where in the cycle the message lands); commands as raw driver writes bypassing components (loses component validation, scoping, and auditability); fire-and-forget commands with no receipt (the UI cannot distinguish failure from delay).
- **Consequences:** Command handling is deterministic and replayable: same model, same input sequence, same commands at the same ticks produce the same run. Targets opt into the operations they accept; everything else rejects with a reason rather than failing silently. The receipt contract gives the UI a uniform answer surface for every operator action.
- **Affected tickets:** #18 (this record); the M2 tickets defining `Command`/`Receipt` in `dcs-core` and wiring command application into the executor boundary; the monitoring transport ticket carrying commands and receipts.

### 8. Monitoring transport

- **Status:** Accepted and implemented in `dcs-monitor` (#20): a synchronous `tiny_http` server holding the executor behind one mutex serves `GET /snapshot`, `GET /receipts`, `POST /command`, and `POST /scan`, with a matching `MonitorClient`. The signal-index endpoint is served as `GET /signals` (#34), bounded history and the journal as `GET /history` and `GET /journal` (#35, decision 17), and the live page at `GET /` (#34, #51); `dcs-controller` serves the surface alongside its paced loop (#48). `dcs-ctl` is the operator command-line tool over the same surface (#153): each subcommand wraps one `MonitorClient` call — reads printing the served payloads, commands printing the receipt or the named `SwitchError` — adding no endpoints and no wire types.
- **Problem:** The monitoring and control UI needs a wire protocol to fetch telemetry snapshots and signal metadata and to submit commands with receipts. The choice should serve the future browser-based UI directly rather than through a gateway, without pulling a heavy stack into the controller.
- **Chosen approach:** HTTP with JSON bodies on the controller process: GET endpoints return the `TelemetrySnapshot` and the model's signal index; a POST endpoint accepts a `Command` and answers with its `Receipt`. Rationale: JSON is already the contract's serialization (decision 3), an embedded HTTP server needs no async runtime or external service, and browser `fetch` plus every scripting tool can consume it. Snapshots report state, not history, so simple polling matches their semantics; if faster updates are needed later, server-sent events or a WebSocket can be layered on without changing the contract types.
- **Alternatives considered:** Newline-delimited JSON over raw TCP (simple and streamable, but browsers cannot open raw TCP — the UI would need a proxy, undermining the direct-access goal); WebSocket as the first transport (native push and browser-friendly, but adds framing and async machinery for a payload that is pull-shaped today); an industrial protocol such as OPC UA (rich semantics, but a heavy dependency premature for a first monitoring path).
- **Consequences:** The first UI and all tests need only HTTP and JSON; wire types are the same serde contracts the runtime already produces. Transport stays replaceable — the contracts live in `dcs-core` and the server only adapts them — so polling cadence and any later push upgrade are deployment choices, not contract changes.
- **Affected tickets:** #18 (this record); the M2 ticket adding the monitoring server to the controller process; future UI tickets.

### 9. Controller process

- **Status:** Accepted and implemented (#19, #48): `dcs-controller <model.json>` loads and validates the model, builds the `SimDriver` and `Executor` through `dcs-assembly` with the `dcs-blocks` registry, paces scans to wall-clock via `--scan-ms`, and — with `--listen` — serves the monitor's endpoints through `Monitor::bind_paced`, refusing `POST /scan` with `409` while the wall clock owns the schedule. `--driven` (#64) is the alternative for an externally paced run: the monitor serves unpaced and each `POST /scan` carries the scan cycle's wiring — a tracking standby's checkpoint pull and the field-owning peer's plant step — inside the request's boundary. `--check` (#160) is the engineering compile-check — chosen as a flag on the existing invocation rather than a `check` subcommand, so the model path stays the single positional argument: it loads, validates, and assembles the model through the standard driver and component registries, prints a deterministic summary of what assembled (devices and components by kind, declared and served points), and exits without a scan running or a listener binding; run-mode options are rejected rather than ignored. Docker packaging exists (#39). `dcs-demo` (#12) remains the fixed-registry M1 example.
- **Problem:** The stack needs a runnable deliverable: a process that loads a plant model, assembles its driver and executor, paces scans to wall-clock time for real operation, and exposes monitoring — without letting wall-clock concerns leak into components, which decision 4 forbids.
- **Chosen approach:** A thin `dcs-controller` binary crate taking a model path (e.g. `dcs-controller <model.json>` plus a scan-period option). It loads and validates the model through `dcs-model`, builds the driver and executor through `dcs-assembly` (decision 6), then runs a loop that paces `Executor::scan` to wall-clock and applies pending commands at the scan boundary (decision 7). The monitoring HTTP endpoints (decision 8) are served alongside the loop, sharing the executor behind the monitor's mutex (#48): paced scans run through `Monitor::paced_scan`, and `POST /scan` is refused (`409`) while pacing because the wall clock owns the scan schedule — externally requested scans would inject ticks no schedule accounts for. The binary holds no control logic and no component code: pacing, transport, and process lifecycle live in this outer shell; everything inside the executor remains virtual ticks.
- **Alternatives considered:** Pacing inside `Executor::run` (leaks wall-clock into the deterministic core and makes runs non-reproducible); per-component timers (rejected with decision 4); control logic compiled into the binary (defeats model-driven assembly — the plant would be code, not a model).
- **Consequences:** The determinism boundary is explicit: inside the executor everything is tick-domain and reproducible; outside it the process paces, serves, and can be stopped, updated, or replaced. The binary is the unit that redundancy (decision 10) later checkpoints and swaps. Tests keep using the unpaced executor, so pacing code stays thin and separately exercisable.
- **Affected tickets:** #18 (this record); the M2 ticket creating the `dcs-controller` binary; the M3 tickets that wrap it in peer management.

### 10. Redundancy direction

- **Status:** Proposed — direction only, recorded as the basis of milestone M3. The enabler it relies on is implemented: the executor's virtual-tick determinism (#9) makes transferred state meaningful. The state-capture half is now also implemented (#21): `dcs-core` carries the `StateMap`/`StateError` contract and driver hooks on `IoDriver`, components carry `capture_state`/`restore_state`, `SimDriver` transfers the simulated field state, and `Executor::checkpoint`/`restore` move a run between executor instances. Peer management and I/O-ownership arbitration are implemented under #46 (decision 15) and proven end-to-end under #64 — the scripted two-process hot swap over the shared simulated plant.
- **Problem:** Per `AGENTS.md`, a redundant controller instance on another machine must take over without interrupting the process: the active controller keeps running while the standby is updated, replaced, or assumes control. This needs a recorded direction before M3 tickets decompose it.
- **Chosen approach (proposed):** Active/standby peers running the same plant model. The standby periodically receives a deterministic checkpoint — executor tick, component state, scan image, and driver-side state — in a serde-serializable form like the rest of the contract, and restores it so that on switchover its next scan produces outputs identical to what the active would have produced (bumpless switchover). Determinism (decision 4) is what makes this work: same model plus same state plus same inputs gives the same outputs on any host. Components and drivers gain checkpoint/restore hooks; a component that cannot checkpoint is reported when the model is built, not at failover. Switchover is a peer-level decision that also moves the field-facing identity — monitoring endpoint and I/O write ownership — to the new active.
- **Alternatives considered:** Restart-based redeploy (interrupts the process — the vision rules it out); lockstep parallel execution of both controllers (doubles I/O ownership questions and adds arbitration complexity for no first-version benefit); stateless takeover replayed from an input journal (requires recording every input and unbounded replay to reconstruct state).
- **Consequences:** Checkpoint/restore becomes a contract on components and drivers, adding hooks to `dcs-core`, `dcs-runtime`, and `dcs-sim` in M3 tickets. I/O ownership transfer — which peer may write the field — needs defined arbitration, initially simulated. The monitoring path (decisions 7 and 8) must follow whichever peer is active, so the UI treats the pair as one logical controller.
- **Affected tickets:** #18 (this record); all M3 "Redundant hot-swap controllers" tickets.

### 11. Checkpoint wire format and versioning

- **Status:** Accepted and implemented (#21): `dcs-runtime::Checkpoint` is a serde type carrying `tick`, `components` (a `BTreeMap` of `StateMap` keyed by component name), `driver` (an `Option<StateMap>`), `outputs` (the scan image's `Out` samples), and `internal` (image-carried `In` samples); `dcs-core` supplies the `StateMap`/`StateError` vocabulary. The deliberate gap this paragraph once recorded — no `version` field, compatibility enforced structurally rather than negotiated — is closed under #66 (decision 27): the checkpoint now carries `format_version` and `model_fingerprint`, and the negotiation runs ahead of the structural checks described here.
- **Problem:** M3 moves a run between controller instances. The checkpoint needs a wire representation consistent with the rest of the contract, and a standby must reject a checkpoint produced by a different model, component set, or build — restoring one silently would leave the standby diverged while looking converged.
- **Chosen approach (implemented):** JSON via serde, like every other contract type (decisions 3, 8). Mismatch rejection is structural and layered rather than version-numbered. Malformed JSON or schema drift fails at deserialization. The checkpoint's component set must equal the standby's registered set exactly — extra names fail `RestoreError::UnknownComponent`, omissions `MissingComponent`. Each element then strictly validates its own `StateMap`: `require_*`/`optional_*` accessors yield `MissingField`/`IncompatibleField`, `ensure_known_fields` rejects fields the element never captured, and out-of-domain values yield `InvalidValue` — every error naming the element and field. Restore is all-or-nothing: any failure returns `RestoreError` and yields no partially restored executor, and the supplied driver validates its whole section before applying any of it. No top-level `version` is carried because a checkpoint is transient peer traffic between same-build instances sharing one model; if checkpoints later cross builds or persist, a version field and migration enter then, mirroring decision 3.
- **Alternatives considered:** An explicit `version` field with on-load migration like the model document (premature — version negotiation would only mask the build skew the strict field checks already catch); an opaque binary encoding (efficient but uninspectable and inconsistent with the JSON contract); lenient restore that ignores unknown fields (silently drops state a newer peer captured — exactly the quiet divergence the design rejects).
- **Consequences:** A restore answers "equivalent run or named failure" — never a partial one. The strictness cuts both ways: a standby built from a different model revision, or components whose captured fields drift, reject rather than degrade, so peer compatibility is same-build, same-model by construction. Each component's `StateMap` field vocabulary is de facto wire contract and must deploy to both peers together.
- **Affected tickets:** #21 (implemented); #32 consumes the format; #46 relies on its tick alignment.

### 12. Peer transport

- **Status:** Implemented (#32). `GET /checkpoint` on the active's monitor serves the serde `Checkpoint`; the standby pulls it — `MonitorClient::checkpoint` — once per scan cycle and applies it in place at its own scan boundary. The pull direction is the implemented one, as proposed below: the standby controls its own resync cadence and an unreachable active is a named, recoverable `Degraded` state rather than corrupted state.
- **Problem:** Checkpoints must move from the active controller to the standby — and later, role and promotion traffic with them. The choice is between reusing the monitoring HTTP+JSON transport and standing up a dedicated peer protocol.
- **Chosen approach:** Reuse the decision-8 transport. `Checkpoint` is already a serde JSON contract and `dcs-monitor` already serializes executor access behind one mutex, so a peer endpoint on the same server carries checkpoints — `GET /checkpoint` for standby pull (the natural shape: the standby controls its own resync cadence and survives active restarts by retrying); `POST /checkpoint` for active push was the rejected direction. Peer traffic and UI traffic share one listener, one serialization discipline, and one executor lock, so a served checkpoint is always a consistent between-scans capture — the active paces its own scans through `Monitor::paced_scan` under that lock — and a standby applies what it receives at its own scan boundary.
- **Alternatives considered:** A dedicated peer protocol on raw TCP (a second wire stack and framing layer for one message type — no first-version benefit); the remote driver's plant protocol implemented in `dcs-sim-net` under #31 (wrong direction — that is controller-to-field, not controller-to-controller); a brokered message bus (an external service M3 does not otherwise need).
- **Consequences:** One transport implementation serves UI and peers; the monitor's serial, one-request-at-a-time handling keeps checkpoint capture and application points deterministic. Under the implemented pull model an unreachable active is a named transfer failure, not corrupted state. Checkpoint cadence is a deployment choice: the payloads are pull-shaped already, so no push machinery is required.
- **Affected tickets:** #33 (this record); #32 implemented it; decision 8 and #20 supply the transport.

### 13. Standby field observation

- **Status:** Implemented. The contract half landed in #21: `IoDriver::capture_state` defaults to `None` and `SimDriver` captures and restores its full simulated field state — point samples, injected faults, process-element accumulators, driver tick. The shared-field half landed in #31: `dcs-sim-net`'s `PlantServer` serves one `SimDriver` plant as a documented line-delimited JSON protocol over TCP (read, write, explicit step, fault injection), and `RemoteDriver` implements `IoDriver` against it — the field-observing kind, `capture_state` left at its `None` default, with server loss surfacing as `Disconnected`/`Timeout` and point failures carried as their `IoError`s.
- **Problem:** A standby must run scans against field values, but "the field" differs per driver kind. A standby-local `SimDriver` holds the process state inside itself and starts at initial values unless state is transferred; a real fieldbus driver holds no authoritative state at all — the plant is the state, observed through its own channels.
- **Chosen approach:** Per driver kind, expressed in the checkpoint's `Option<StateMap>` driver section (decision 11). A standby-local `SimDriver` restores the captured section and thereafter steps its own copy of the simulated process. A field-observing driver — real hardware, or the remote simulated driver implemented under #31 — leaves `capture_state` unimplemented, the checkpoint carries no driver section, and restore skips it: the standby reads the actual shared process through its own connection. For M3's two-process demonstration the remote simulated driver is the field-observing kind: both peers attach to one shared simulated plant over TCP (implemented in `dcs-sim-net`, #31), so the standby observes what the active's writes actually did, proving the abstraction boundary redundancy depends on.
- **Alternatives considered:** Always restoring driver state (incoherent for field-observing drivers — they hold no state to restore); a standby scanning without any field view until promoted (cannot track the run or expose divergence before switchover); both peers writing the field continuously (violates single-writer ownership — see decision 15's gate).
- **Consequences:** Driver state capture is a per-driver-kind contract: checkpoint consumers must tolerate a missing driver section, and driver implementors decide which kind they are. The two standby modes differ in fidelity — a standby-local `SimDriver` diverges if it misses a checkpoint, while a shared-field standby tracks continuously — and #32's tests (`dcs-controller/tests/standby.rs`) exercise both: the local-sim standby resynchronizes its private plant from the driver section, the remote standby tracks the shared plant and is output-quiescent behind `dcs_runtime::WriteGate`.
- **Affected tickets:** #21 (implemented contract); #31 (implemented shared-field driver); #32 implemented the two standby modes.

### 14. Internal and operator points

- **Status:** Implemented (#30): channel-less internal points are first-class model declarations, served from the executor's scan image. `Command::WriteValue` applies at the documented scan boundary (#20), restricted by the model-declared `writable` flag (#49, decision 18). `dcs-demo`'s own `assemble` keeps the precursor mechanism — port-to-port carriers as `Out`/`In` pairs on a reserved simulated device joined by a driver `Loopback` (#12).
- **Problem:** Two point populations are not field I/O: operator values — setpoints and mode switches that live in the controller as command targets — and port-to-port carriers, the component-to-component signals the model wires without a channel. Both need a model representation consistent with the single-contract goal, observable in telemetry, and checkpointed like field points.
- **Chosen approach:** An `io_point` may declare no `channel`; it must then carry an `initial` value of its declared `value_type` (a channel-bound point must not declare one). In `dcs-runtime` the point map records `internal: Option<Value>` per point: the image seeds internal points at wiring, an internal `In` point holds its initial until a command writes it through the receipt-answered command path, and an internal `Out` point records component writes for monitoring — the driver is never touched. `PointMap::with_internal_link` routes an internal `Out` sample onto an internal `In` point at each scan's input phase — the image-carried equivalent of a field loopback, delivering one scan later. In `dcs-assembly`, channel-less points join the point map without a channel binding; port-to-port connections synthesize a linked internal pair, and a point-to-point connection between declared internal points becomes a link — a mixed field/internal pair is `MixedPointLink`. Direction and value-kind checks apply to internal points exactly as to field points, and malformed declarations are named errors in validation (`MissingInitial`, `InitialKindMismatch`, `FieldInitial`) and assembly (`InvalidInternalPoint`). The `writable` flag (#49) then narrows the command surface to model-declared points, making operator values an explicit, audited subset rather than "any known point".
- **Alternatives considered:** Commands addressed to component parameters directly (parameter maps are construction-time input, not scan-time state — a point target keeps the command path uniform); port-to-port wiring as invisible executor plumbing (the carrier would be absent from the point map, telemetry, and checkpoints — an unobservable signal); keeping the demo's synthesized-device convention as the permanent answer (works, but every model consumer must rediscover it — the schema should carry the concept).
- **Consequences:** Internal points make operator values and inter-component signals first-class citizens of the one model: visible in `TelemetrySnapshot`, writable through the receipt-answered command path, and carried in checkpoints — the `outputs` section covers internal `Out` samples and a new `internal` section carries internal `In` samples, so a commanded setpoint survives switchover rather than reverting to its declared initial. The `initial` and `channel` fields serialize as optional, so documents written before internal points existed still load under the same model version.
- **Affected tickets:** #12 and #20 implemented the precursor mechanics; #30 implemented the model-level contract; #49 implemented the writable flag; #33 (this record).

### 15. Switchover semantics

- **Status:** Implemented (#46). The role contract is `dcs-core`'s serde `Role` (`active`, `standby`, `promoting`, `demoting`), `StandbySync`, `RoleReport`, and `SwitchError`; `dcs_runtime::Peer` is the role machine wrapping the executor, applying `promote`/`demote` at the request's scan boundary — the gate moves with the request, the reported role settles on the first scan under the new mode — and refusing with the named `SwitchError`s (`NotConverged`, `AlreadyActive`, `NotActive`). The monitor serves them as `GET /role`, `POST /promote`, and `POST /demote`, journals each reported transition as `JournalEvent::RoleChanged`, and refuses commands on a non-active peer with `CommandError::NotActive`. `dcs-controller --standby ADDR --listen ADDR` is the promotable standby; every instance whose driver surface reaches the shared field assembles behind a `WriteGate` — a `--remote` attachment behind full coverage, a registry fan-out declaring `sim-tcp` devices behind `closed_covering` over the `DeviceBackend.field_facing` points so a tracking peer's local simulated backends keep stepping while its field writes are quiesced (`FanoutDriver::step_local` likewise leaves field-facing backends' clocks to the field owner). The acceptance test `dcs-controller/tests/promotion.rs` proves bumplessness over the shared plant: after the switch the promoted peer's snapshots equal the uninterrupted run the demoted peer still computes. The process-level scripted run — a `dcs-plant-server` owning the plant, two `dcs-controller --driven` peers on one `sim-tcp` model, and an uninterrupted reference run — lands under #64 (`dcs-controller/tests/hot_swap.rs`), deterministic across repeated runs.
- **Problem:** A tracking standby must be able to become the active without a missed, duplicated, or divergent field write — the vision's hot-swap requirement. This needs recorded semantics before code: who may write the field, when the change takes effect, and what "bumpless" demands.
- **Chosen approach (implemented):** A role contract — `active`, `standby`, and transition states — as serde-serializable monitoring types, so the UI treats the pair as one logical controller. While standby, the executor scans and tracks checkpoints (decisions 11–13) but its `Out` writes are quiesced behind a write gate at the driver boundary — a gating `IoDriver` wrapper or a mode on the shared remote driver — while `In` reads still observe the field. A promotion request lifts the gate at a documented scan boundary, so the first post-promotion scan writes exactly what the checkpointed run would have written — bumpless by determinism (decision 4). Demotion re-quiesces the old active, preserving the invariant that exactly one peer writes the field at a time. Promotion is operator- or test-triggered; automatic failure detection is out of scope. Promoting a standby that has not converged, or promoting twice, fails with a named error rather than diverging.
- **Alternatives considered:** Lockstep both-write redundancy (rejected with decision 10 — double writers need arbitration at every field device); a halted standby cold-started on failure (missed scans and lost state — a restart, not a swap); mid-scan promotion (a timing-dependent effect, against decision 4's determinism); automatic heartbeat failover (premature machinery — a follow-up once the manual semantics are proven).
- **Consequences:** "Bumpless" is a property of a converged standby: the gate, the promotion boundary, and the convergence check are all required pieces. The gate must sit at the field-facing boundary — quiescing the standby's writes to the shared field without freezing the image-carried or locally simulated state it needs to keep tracking. Role reporting on the monitoring surface gives the UI its single-logical-controller view (decision 10).
- **Affected tickets:** #33 (this record); #46 implemented it; #32 supplied the tracking standby and #31 the shared field.

### 16. Component self-description

- **Status:** Accepted and implemented (#50, #61, #62): `ComponentDescriptor`/`PortDescriptor`/`PortRole`/`ParameterDescriptor`/`ParameterRange` are serde contract types in `dcs-core`; `Component::describe` derives a correct default and every `dcs-blocks` kind overrides it beside its `KIND` and `from_parameters`; `TelemetrySnapshot.descriptors` serves one descriptor per component in scan order. Descriptor-driven range enforcement of operator tuning is implemented (#82, decision 20), and the descriptor-driven faceplates are implemented (#62): the page renders one faceplate per instance from the served descriptors — role hints picking the conventional elements, parameters listed with kinds and ranges, diagnostics joined by name — degrading to the generic name-plus-diagnostics-plus-wired-points view for a kind with no custom descriptor.
- **Problem:** The monitoring UI must render each component instance — a faceplate with its live values, tunable settings, and state — without hand-building a view per component kind, or the vision's "no per-layer engineering" goal fails at the UI layer. What the UI can fetch today does not say how to draw a component: the snapshot carries only diagnostics counters per instance, and the model's `kind`/`ports`/`parameters` describe wiring, not semantics — nothing says which port is the process value versus the setpoint, or which parameters are operator-tunable.
- **Chosen approach (implemented):** A serde `ComponentDescriptor` type in `dcs-core` — beside the other contract types the UI already consumes — with one descriptor per registered component kind. A descriptor names the kind and describes its surface: ports (name, direction, value kind, and a small closed set of semantic roles such as process-value, setpoint, command, feedback), parameters (name, value kind, required or optional, constraint hints), and faceplate hints (which elements the default rendering shows and which are trend candidates). Each `dcs-blocks` kind supplies its descriptor beside `KIND` and `from_parameters`; the component registry (decision 6, #19) collects them and the monitor serves them to the UI over the decision-8 transport. The page joins three already-modeled things — descriptor (kind semantics), `ComponentInstance` (this instance's wiring and parameters), and live point telemetry (the values) — and renders any registered kind generically. An instance whose kind serves no descriptor degrades to a generic name-plus-diagnostics-plus-wired-points view, never an error.

The port-to-point wiring the join needs stays inside the serde contract (#62): `PortDescriptor` carries an optional `point` — the `PointId` the instance's port is bound to — which the executor annotates when it serves the descriptor, joining each port to the point its same-named declared `IoRequirement` resolved to. A kind-level `describe()` reports `None` — the binding is instance wiring, not kind semantics — and the field serializes only when populated, so payloads predating it still parse and a port no declared requirement backs serves as unwired. The alternative — the monitor serving the loaded model's component and connection sections for the page to re-resolve — was rejected: it exports the wiring resolution to every consumer and duplicates the executor's already-checked binding work, where the annotation keeps the whole contract in the shared serde types.
- **Alternatives considered:** Per-kind UI code in the page (per-kind engineering is exactly what the vision rules out); serving per-kind view templates (a second artifact to version and ship, plus the safety surface of remotely supplied markup); deriving the faceplate from `IoRequirement`s alone (they carry resolved per-instance point bindings — name, direction, kind — but no semantic roles or parameter semantics; the descriptor adds exactly that layer); embedding descriptors in the model document (duplicates kind-level data into every model and splits the source of truth between schema and component code — the registry keeps one).
- **Consequences:** Adding a component kind means supplying one descriptor next to its constructor — control behavior, monitoring data, and UI representation arrive together, per the vision. The descriptor vocabulary is a contract like every other `dcs-core` type, so UI, runtime, and blocks version together; it must stay small and generic, and kinds needing genuinely bespoke views degrade to the fallback rather than growing the vocabulary. Descriptor serving joins the metadata surface, so the UI needs no extra transport.
- **Affected tickets:** #53 (this record); #50 implements the contract and per-kind descriptors; #61 completed the per-kind descriptors; #62 implements the faceplates and the bound-point annotation; relies on #19 (registry), #34 (metadata serving), and decisions 6 and 8.

### 17. History and journal consumption

- **Status:** Accepted and implemented (#35): `dcs-monitor` records a per-point history ring and the transition journal once per completed scan — after the write phase, never mid-scan — bounded by `MonitorConfig` with oldest-first eviction and never-reused `seq`s, and serves `GET /history` (repeatable `point` selection plus `since`) and `GET /journal?since=…`. The contract types (`HistorySample`/`PointHistory`, `JournalEntry`/`JournalEvent`) live in `dcs-core` per decision 8; journaled events are quality changes, settled command receipts, and component step failures — role changes (decision 19) join when #46 lands. The page panes consuming the streams — per-point trends on `/history` and the journal pane on `/journal`, both polled on the snapshot's cadence — are implemented (#51). Implemented basis: `TelemetrySnapshot` deliberately reports state, not history (#10); the executor's in-memory receipt log is the first journal-like record, served by `GET /receipts` (#20); all timestamps are already virtual `Tick`s (decisions 2, 4).
- **Problem:** Trend and event views need sequences, not point-in-time state: a trend wants each point's recent samples and a journal wants the run's transitions — commands applied or rejected, quality changes, component errors. A UI polling `/snapshot` cannot reconstruct either: samples between polls are lost, and a transition that begins and ends between polls is invisible.
- **Chosen approach (implemented):** The producer records bounded history server-side, in the tick domain. A per-point ring retains each point's recent `Sample`s; a transition journal is an ordered log of events — command applied/rejected, point quality transitions, component step errors, and later role changes (decision 19) — each stamped with its tick. Both carry fixed capacity with oldest-first eviction and a monotonically increasing sequence number per stream, so a consumer detects a gap instead of silently missing entries. The monitor serves them as GET endpoints with since-cursors — `GET /history` (point selection plus since) and `GET /journal?since=…` — and the UI polls them incrementally on the same cadence it already polls `/snapshot`: order-of-seconds, far slower than the scan period, refetching only entries newer than its last seen sequence. Tick stamps keep journal, history, snapshots, and receipts in one comparable timebase.
- **Alternatives considered:** Reconstructing history by polling snapshots at scan rate (a lagging page still misses samples, and per-point series would transfer unboundedly); unbounded server-side logs (memory growth a long-running controller cannot accept — #35 specifies bounded); push streaming over SSE or WebSocket (decision 8 already deferred push — cursor polling fits the pull-shaped contract, and a push layer can be added later without changing these types); persisted history on disk (durability machinery M4 does not need — history is volatile diagnostics and re-accumulates after a restart).
- **Consequences:** Executor and monitor gain fixed-size buffers — memory stays bounded as a deployment constant — and the UI stays poll-shaped, consistent with decision 8. Consumers must tolerate sequence gaps; the numbers make them visible rather than silent. The journal becomes the audit surface for operator actions, complementing per-command receipts with one ordered run record.
- **Affected tickets:** #53 (this record); #35 implements the buffers and endpoints; #51 builds the consuming panes; relies on the #20 transport and the #10 snapshot contract.

### 18. Operator command surface

- **Status:** Implemented (#49): `IoPoint` carries the optional `writable` flag, validation rejects it on `Out` points, assembly propagates it into the `PointMap`, `submit_command` refuses unmarked points and every `Out` point with `CommandError::NotWritable` at submission, the signal index reports the mark, and the page's command form offers only writable points. The command contract (#20, decision 7) supplied the receipts and the scan boundary; the channel-less internal points most operator values occupy came from #30 (decision 14).
- **Problem:** As implemented, the command surface is "every mapped point": `WriteValue` accepts field `In` points the process drives and `Out` points a component overwrites next scan, so writes that cannot meaningfully stick are still accepted. The model does not say which points an operator may command, and the UI cannot distinguish a legitimate setpoint entry from a write destined to be overwritten — it learns only through receipts after the fact.
- **Chosen approach:** The plant model declares the writable surface: an optional `writable` marker on `IoPoint` (decision 14, #49), defaulting to unset so documents predating it load unchanged under the same model version. The mark is honored on `In` points only, and the recorded rule for `Out` points is rejection — `WriteValue` commands never target them, and validation reports `writable` on an `Out` point as `WritableOut`, because control logic stays authoritative over outputs inside a scan and operator influence on an output is engineered through components. The flag rides the point into the executor's point map (`PointSpec::writable`), and `submit_command` rejects a command on an unmarked point or any `Out` point at submission with `CommandError::NotWritable` carrying the point — before queuing, alongside the existing unknown-point and type-mismatch rejections. Per kind: a writable field `In` point's command write is forwarded to the driver at the scan head and read back by the same scan's input phase — documented operator substitution of the input image, holding until the field side asserts a different value — while a writable internal `In` point takes the write in the image and holds it until the next command, the common target for operator values like setpoints. Writability joins the point metadata the UI already fetches (the signal index, #34), so the page renders command affordances only where commands can succeed and everything else stays read-only telemetry.
- **Alternatives considered:** Inferring writability from direction or kind (no direction maps to "operator-writable" — field `In` points are driven by the process, internal `In` points are not, and only the model knows which is which); an executor-side allowlist configured beside the model (a second authority for the same fact, breaking the single-contract goal); UI-only hiding of non-writable affordances (cosmetic — the controller still accepts the commands and the journal still records them).
- **Consequences:** The writable surface becomes explicit, auditable model data; rejection happens at submission with a named reason, keeping the receipt contract uniform (decision 7). Because the flag is schema-optional (decision 3) it defaults to non-writable — models must opt operator points in, and existing models gain the restriction without a version bump. The UI's affordance set derives from the same metadata fetch that drives its displays.
- **Affected tickets:** #53 (this record); #49 implements the flag and the rejection; #30 supplied the internal points operator values occupy; #20 implemented the permissive baseline; decisions 7 and 14.

### 19. Monitoring under redundancy

- **Status:** Implemented — contract under #46, the pair view under #63; the divergence gate of decision 26 joins the same role surface under #88. `GET /role` serves the serde `RoleReport` — `Role` plus the standby's `StandbySync` convergence — on each peer's monitor; `POST /promote` and `POST /demote` answer the post-change report or `409` with the named `SwitchError`; commands submitted to a peer not reporting settled `active` are refused with a `CommandError::NotActive` rejection receipt; and each reported transition is journaled as `JournalEvent::RoleChanged`, keeping roles, history, and snapshots on the one tick timebase. The view half: `dcs-monitor::PairClient` is configured with both peers' monitor addresses, polls each `/role`, sources data from the settled-active peer (a `promoting` peer while a switch settles), routes commands only to a peer reporting `active` with one re-poll-and-retry on a `NotActive` rejection, and reports an unreachable peer as the named `PeerStatus::Unreachable` redundancy fault; the page carries the same logic — configured by `?peer=<host:port>` URL parameters beside its serving origin, rendering the active's telemetry plus a per-peer pair-health section, merging trend and journal feeds across a source switch by the shared tick domain, with cross-origin reads enabled by `Access-Control-Allow-Origin` on the JSON endpoints. - **Problem:** Under M3 the UI faces two controller processes — an active and a standby — that are one logical controller to the operator (decision 10). The UI needs a recorded rule for which peer to display and command, how it behaves across a promotion, and how to avoid presenting the quiesced standby as a second controller or a divergent plant.
- **Chosen approach (implemented contract):** The pair exposes role on the monitoring surface: each peer reports its role — `active`, `standby`, and the transition states of decision 15 — as the serde `RoleReport`, served on its own monitor at `GET /role`. The UI is configured with both peers' addresses, polls each for role alongside its normal cadence, and renders one logical controller from the active's telemetry; the standby contributes pair health — reachability and checkpoint convergence — not a second faceplate set. Commands go only to the peer reporting `active`; a command landing on a standby or mid-transition peer is rejected with `CommandError::NotActive` and the UI retries after re-polling roles. Tick continuity is the divergence check: after promotion the new active's snapshots continue the same tick sequence, so the history and journal panes (decision 17) carry on seamlessly.
- **Alternatives considered:** A gateway endpoint fronting the pair and hiding roles entirely (another deployed component, and the UI learns nothing about redundancy health); polling both peers and merging their telemetry (merge rules risk double-rendering the quiesced standby's suppressed writes); DNS- or virtual-IP-based failover (network machinery, and the standby becomes unobservable — no convergence badge); presenting the pair as two controllers (violates the vision's one-logical-controller requirement).
- **Consequences:** Redundancy becomes visible without being duplicative: one faceplate set plus pair health. Role reporting joins the monitoring contract so every consumer handles pairs uniformly, and transition windows resolve by re-poll rather than push machinery — consistent with decision 8. An unreachable standby is displayed as a redundancy fault, not a plant fault, so the UI needs per-peer connectivity handling regardless.

### 20. Component-targeted commands

- **Status:** Accepted and implemented (#82): `Command::SetParameter { component, name, value }` addresses the component by the name its descriptor and diagnostics report, `Executor::submit_command` validates it against the component's declared `ParameterDescriptor`s — existence, value kind, and a declared `ParameterRange` — and applies it at the same scan head as `WriteValue` through the `Component::apply_parameter` hook, whose default is a named `UnsupportedParameter` rejection. Every `dcs-blocks` kind implementing the hook folds its writable parameters into `capture_state`, so a tracking standby inherits runtime tuning through the ordinary checkpoint (decision 11).
- **Problem:** Operators tune a running plant — PID gains, alarm limits, filter constants — without redeploying it. Today the only command target is a point, and component parameters are construction-time input read once by `from_parameters`: changing one means editing the model and reassembling the executor, which is a redeploy, not an operator action. The component-instance half of decision 7's "a component instance or a point" target remains unimplemented.
- **Chosen approach (proposed):** A new serde `Command` variant — `set_parameter { component, name, value }` — addressing the component by the name its descriptor and diagnostics report, applied at the same documented scan boundary as `WriteValue` and answered by the same receipt contract. - **Alternatives considered:** Retuning through a revised model document (a redeploy that breaks the very run being tuned; the deliberate rolling-update path of decision 25 is intentionally heavyweight); routing tuning through shadow `In` points a component reads as parameters (works on the implemented path, but splits the tunable surface across point wiring and parameter maps, and no declared range bounds the write); a free-form command string (untyped, unauditable, unenforceable — the receipt contract cannot name what failed).
- **Consequences:** Tuning becomes a receipted, journaled operator action whose enforcement authority is the same descriptor that draws the faceplate — the metadata that shows a parameter also bounds its edit. Parameters join checkpointed run state, so each kind's `StateMap` vocabulary grows and deploys to both peers together, per decision 11's strictness. Kinds that must stay fixed simply keep the default rejection.

### 21. Input forcing

- **Status:** Accepted and implemented (#84): `Command::ForcePoint`/`Command::UnforcePoint` are serde commands in `dcs-core`; the executor holds a deterministic `BTreeMap` force set applied at the scan-head command boundary; `TelemetrySnapshot.forces` lists `ForcedPoint { point, value }` entries for the page's badge; the `Checkpoint` carries a `forces` section validated on restore (`RestoreError::UnknownForce`/`IncompatibleForce`); and the journal records both commands as ordinary `CommandSettled` receipts beside the `QualityChanged` transition to `Substituted` their application produces. Implemented basis going in: `QualityReason::Substituted` already names exactly this case in the signal model (#5, decision 2); `Command::WriteValue` to an `In` point already stages a value the scan observes once — but the field driver owns the point thereafter, so wherever the field keeps driving, the substitution is one-shot (#20); and the journal, snapshot, and checkpoint machinery a force set rides on are in place (#35, #10, #21).
- **Problem:** Commissioning and fault-finding need the control-systems notion of a force: pin a field input at an operator-chosen value across scans while the rest of the plant keeps running. A `WriteValue` to an `In` point cannot express this — the driver's next read reasserts the real value, or a loopback or process element overwrites it — and nothing marks a substitution as persistent and deliberate.
- **Chosen approach (implemented):** A dedicated `force_point`/`unforce_point` command pair — chosen over a flag on `WriteValue` so the one-shot write path keeps its existing contract unambiguous — acting on a model-declared *writable* `In` point. While forced, the scan's input image holds the forced value stamped `Quality::Uncertain(QualityReason::Substituted)` every scan and the driver read is bypassed, so components and the UI see substitution, never false `Good` data; a `WriteValue` to a forced field point still reaches the driver — the force overrides the image, not the field — so release observes the field's current value. Release resumes live reads at the next scan boundary — the same documented application point every command uses — so the releasing scan already reads the field again. The force set is run state: listed in the `TelemetrySnapshot` so the page can badge forced points, journaled on force and release (decision 17), and carried in checkpoints so a standby preserves forces through a switchover — a checkpointed force entry is accepted only where the standby's map serves a writable `In` point of matching kind. Forcing a non-writable point or an `Out` point rejects at submission with a named `CommandError`; the writable flag (decision 18) thus bounds the force surface exactly as it bounds ordinary writes. The same surface covers writable internal `In` points — a force overrides even an internal link's routing onto the point — and `unforce_point` on an unforced point applies as a no-op.
- **Alternatives considered:** Driver-side forcing, e.g. a `SimDriver` fault-style override (bypasses the executor's image, cannot reach field-observing drivers, and reports no substituted quality into the scan); forcing stamped `Good` (hides the substitution the quality model exists to expose); engineering an `OverrideSelect` per forceable input (a control-logic feature — permanent interlocking in the model, not an ad-hoc commissioning action).
- **Consequences:** A force is an explicit, audited, checkpointed deviation between the field and the scan image: the journal answers when it was applied and released, the snapshot answers what is forced now, and a restored standby forces identically. Determinism is preserved — forces apply and release at the scan boundary like every other command. The writable surface a force acts on is implemented under #49 (decision 18).
- **Affected tickets:** #89 (this record); #84 implements it; depends on #49 (writable points); relies on #20, #35, and #21; decisions 2, 7, 14, and 18.

### 22. Driver health and scan overruns

- **Status:** Implemented (#83): `TelemetrySnapshot` carries an `io_health` section — `IoHealth` holding `failed_reads`/`failed_writes` totals, a `consecutive_failures` streak over boundary operations, the `last_error` as an `IoFault` (tick, point, direction, `IoError`), the `scan_overruns` count, and the driver's `DriverDiagnostics` (`link` as a `LinkState`, `last_error` description) — all serde types in `dcs-core`; the executor counts at the read and write boundaries where it already degrades samples or fails the scan; `IoDriver::diagnostics` defaults to `None` and `RemoteDriver` implements it, `WriteGate` forwards it, `FanoutDriver` aggregates it per backend; the paced scan loop feeds overruns through `Executor::record_scan_overrun` reached via `Peer`/`Monitor`; and the monitoring page renders the section as its own line beside per-point quality.
- **Problem:** Field-communication trouble currently surfaces only per point — a `Bad` sample here, a `ScanError` there — so the UI cannot answer "is the I/O subsystem healthy", nor distinguish one bad sensor from a dead field link: a `RemoteDriver` whose plant server is down reports the same per-point errors a single failed channel would, and link state is invisible. A paced controller that overruns its scan period likewise degrades silently — nothing counts it.
- **Chosen approach (implemented):** A named I/O-health section on `TelemetrySnapshot`, as serde contract types in `dcs-core` like every other monitoring type. The executor collects counters at the boundaries it already owns: failed-read and failed-write totals, a consecutive-failure count reset by any successful boundary operation, and the last `IoError` with the tick and point it hit. Beneath that, an optional `IoDriver::diagnostics` hook — default `None`, mirroring `capture_state`'s per-kind optionality — lets a driver report transport-level health: `RemoteDriver` reports link state and its last protocol failure, so a dead plant server reads as link degradation distinct from per-point faults. Scan overruns are the third surface: the pacing shell counts scan periods it overshot and feeds the counter through `Executor::record_scan_overrun` — wall-clock failure data enters the snapshot from outside the executor, which stays tick-domain per decision 4.
- **Alternatives considered:** Deriving health from per-point quality in the UI (loses the link-versus-point distinction and forces every consumer to re-aggregate); logging overruns to stderr only (invisible to the contract, the snapshot, and the journal); letting the executor detect overruns from a wall clock (rejected with decision 4 — nondeterminism inside the core); a mandatory driver-diagnostics method (breaks drivers that have nothing transport-level to report — optionality mirrors `capture_state`).
- **Consequences:** I/O health becomes contract data the UI, the journal, and tests read identically — the page renders it as a health line separate from per-point quality — and driver diagnostics stay per-kind optional so `SimDriver`, `RemoteDriver`, and future fieldbus drivers implement or skip it honestly; wrapping drivers forward or aggregate (the gate passes the field link's health through; the fan-out reports any reporting backend's link). The counters describe the producing run's own driver experience and are not checkpointed — a standby's health is its own driver's. Overrun reporting keeps pacing's wall-clock concern outside the deterministic core — the counter is a report, never an input — and identical runs produce identical health payloads.
- **Affected tickets:** #89 (this record); #83 implemented it; relies on #9, #10, #31, and #48; decisions 4 and 5.

### 24. Plant-side dynamics as declared data

- **Status:** Implemented (#81): `dcs-plant-server --dynamics FILE` merges a plant-side dynamics document — a JSON list of `ProcessElement` declarations in the `ChannelMap` vocabulary (`first_order_lag`, `second_order_lag`, `integrator`, `dead_time`, `noise`) — into the resolved `sim_channel_map`, validating each element as it merges so a rejection names the element and the point it drives. The document deliberately carries no `version`: it is a plain declaration list beside the model, and widening the element vocabulary extends it the way `ChannelMap` itself evolves. Basis: the `ProcessElement` vocabulary — `FirstOrderLag` and `Integrator` (#8), `DeadTime` (#37), `SecondOrderLag` (#135), `Noise` (#156) — stepped deterministically by `SimDriver::step` and checkpointed as element accumulators (#21); `dcs-assembly::sim_channel_map`'s open seam (#19); `PlantServer` serving a map's elements to remote drivers (#31). The second-order lag's recorded parameterization is `time_constant` (τ = 1/ωₙ) plus `damping_ratio` (ζ) — the standard `τ² y'' + 2ζτ y' + y = u` form, chosen over a two-time-constant cascade because ζ < 1 produces the overshoot the parameter-tuning path needs — stepped by the exact zero-order-hold discretization like the first-order lag's exact update. The noise element's recorded parameterization is `amplitude` plus `seed`: each `Good`-input step draws once from a splitmix64 generator — the `u64` state advanced by the golden-ratio increment, then the standard mix, the top 53 bits scaled into [0, 1) — and outputs `u + amplitude·(2x − 1)`, holding the output within `u ± amplitude`. A seeded generator was chosen over a declared disturbance table because it gives an unbounded, exactly replayable deviation sequence without authoring data: identical seeds replay identical sequences, distinct seeds produce distinct ones, and the carried `u64` state checkpoints and restores mid-sequence like every element accumulator.
- **Problem:** The simulated plant's behavior — which elements drive which points, their time constants, delays, and initial values — is real engineered content, but it lived in Rust call sites: `dcs-demo` built its `FirstOrderLag` inside `assemble`, and a shared plant server could not serve a declared plant without code. The obvious alternative — process elements inside `PlantModel` — would couple the control contract to testbench physics: a real plant has no such declaration, and the model's job is to describe the controller's view, not the world's.
- **Chosen approach (implemented):** Plant-side dynamics are declared data in a document *beside* the model, not schema *inside* it: a JSON list of `ProcessElement` declarations naming the points each element drives. `dcs-assembly`'s open `sim_channel_map` seam is the join — `dcs-plant-server` loads the model for the control contract and the dynamics document for the physics, merging them into the `ChannelMap` it serves. The plant model stays the single contract for control; the dynamics document is the testbench's account of the process it stands in for — engineered and validated, never read by a controller.
- **Alternatives considered:** Elements as `PlantModel` schema (the contract would carry simulation-only content real deployments cannot produce, and every consumer would have to know which sections are testbench); keeping dynamics in Rust constructors (the pre-#81 status quo — works for `dcs-demo`, but the shared plant server and every integration rig then need code to describe the same plant); folding dynamics into device `kind` strings (opaque, unvalidated, and duplicating point identity the model already owns); a versioned document like the model's (decision 3's discipline is for a long-lived cross-consumer contract — the dynamics list is simulation tooling's own format, so a bare declaration list suffices until it grows one).
- **Consequences:** The simulated plant is declaratively reproducible — `dcs-plant-server` and test rigs load the same document instead of reimplementing physics, and the scripted-scenario device kind (#67) gets a sibling pattern for declared behavior. The boundary stays explicit: the model describes what the controller sees, the dynamics document describes what the world does. Checkpointing already treats element accumulators as driver state (decision 13), so the redundancy path needs no change.
- **Affected tickets:** #89 (this record); #81 implemented it; #67 follows the same declared-behavior pattern. Implemented basis: #8, #12, #21, #31, #37.

### 25. Rolling model-revision deployment

- **Status:** Implemented (#87). The standby's checkpoint pull is `Peer::transfer`, which routes on the fingerprint negotiation (decision 27): a matching fingerprint applies as ordinary convergence exactly like `Peer::apply`; a foreign fingerprint on a peer armed by `dcs-controller --revised` (`Peer::with_revision`) crosses the model boundary through `Executor::reinitialize`, while an unarmed peer still degrades on the mismatch — a revision is a declared intent, never an assumption. The crossing classifies every checkpoint section before applying anything, so a refused revision leaves the revised run untouched: carried are writable internal `In` points matched by declared point id and value kind, `Out` image samples the revision still declares, and the force set under the same writability and kind rule; named dropped in the `dcs_core::CarryoverReport` are checkpointed points the revision does not serve, synthesized link points whose allocated ids are not declared identity, checkpointed component state whose name the revision does not register, and driver state — component and driver state always reinitialize (no per-kind compatibility rules exist yet, and tuned parameters ride the checkpoint's component section, so a tuning-preserving revision must keep the component's declared identity). The armed peer reports `StandbySync::Reinitialized` carrying the report — source and destination fingerprints, resumed tick, the carried and dropped and initialized sets — journaled once per transition as `JournalEvent::Reinitialized`; `promote` and `self_promote` accept it beside `Tracking`, so the documented demote-then-promote order (decision 15) moves the field writer to the revised model at a scan boundary with exactly-one-writer preserved. A carryover break — a retyped carried point, an unserved force, an unsupported checkpoint version — is a named `CarryoverError` the peer reports as `Degraded`, and `POST /promote` answers `not_converged` with that state. The scripted rig is `crates/dcs-controller/tests/model_revision.rs`: a `dcs-plant-server` tank loop with a v1 active and a `--revised` v2 standby runs the full revise-reassemble-promote path asserting the named carryover outcomes, the breaking-change refusal before promotion, and bit-identical repeats.
- **Problem:** Plant engineering changes in service — a retyped point, a new component instance, rewired connections — produce a revised model the running pair must adopt without interrupting the process. A checkpoint cannot carry a run across model revisions: decision 11's strictness makes the mismatch a named rejection, which is correct for same-model peers but leaves no path for intentional change.
- **Chosen approach (implemented):** Model revision is a deliberate rolling deployment through the redundant pair, not a synchronization. The standby loads the revised model, validates and reassembles against it, and enters a named `reinitialized` state — distinct from `converged`, since no checkpoint carried it there. A documented carryover rule decides what crosses the model boundary: operator-writable internal points (decisions 14, 18) matched by declared identity carry their last values; component state reinitializes by default unless a documented per-kind compatibility rule applies; and every element that cannot carry over is named in a carryover report rather than silently dropped. Promotion then moves the field writer to the new-model instance at a scan boundary with demotion of the old peer (decision 15), preserving exactly-one-writer throughout; a revision that breaks a carryover rule fails before promotion with named errors.
- **Alternatives considered:** Restart-based redeploy (interrupts the process — the vision rules it out); a lenient restore mapping old state onto new components field-by-field (silent divergence — exactly what decision 11's strictness exists to prevent); dual-running old and new revisions with output comparison (doubles the field-writer question and defines no merge for differing control logic).
- **Consequences:** In-service model change becomes an engineered, auditable operation: the carryover report is the record of what survived the revision, and `reinitialized` is an honest state the UI can display instead of a false convergence. Component kinds that want tuning-preserving upgrades document per-kind compatibility rules — the same obligation decision 20 puts on runtime tuning. The mechanism composes existing pieces — load, validate, assemble, promote — rather than adding a second deployment path.
- **Affected tickets:** #89 (this record); #87 implements it; #114 adds `dcs-model diff`, the human-facing review surface reporting what a revision adds, removes, and changes before the pair rolls it; relies on #46 (promotion), #66 (fingerprinted checkpoints), and #32 (standby machinery); decisions 10–15.

### 26. Standby divergence detection

- **Status:** Implemented (#88): `dcs-runtime`'s `Peer` stashes each non-field-owning scan's staged field `Out` image (`Executor::staged_field_outputs`, the writes the scan would have issued through the closed `WriteGate`) and, when an applied checkpoint's tick equals the stashed tick, compares it point by point against the peer's own reads of the same `Out` points through its driver surface (`divergence::compare_staged`). A mismatch moves the peer to the named `StandbySync::Diverged` carrying the `Divergence` evidence — point, staged value, field value — and `promote` refuses it with `SwitchError::NotConverged` carrying that state; the gate stays closed throughout. A fresh checkpoint whose same-tick staged image compares cleanly restores `Tracking`, and the transition is journaled as `JournalEvent::DivergenceDetected` at the compared tick and rendered beside the convergence state on the monitoring surface.
- **Problem:** A checkpoint-converged standby can still diverge — skewed parameters, a plant restart, a missed transfer — and nothing would notice until it promotes and writes wrong outputs to the shared field. As implemented, `StandbySync::Tracking` means "the last checkpoint applied cleanly", not "proven to track the run".
- **Chosen approach (implemented):** The standby proves tracking before it may promote. While quiesced it stages the `Out` writes its scan would issue; the field-side truth is the standby's **own reads of the same `Out` points** through its driver surface — the field-observing path it already uses for inputs, needing no plant-server record and seeing exactly the field the standby would write. The per-value-kind rule is documented in `dcs-runtime::divergence`: `Bool` and `Int` compare exactly, `Float` agrees within `FLOAT_TOLERANCE = 1e-9` relative to the larger magnitude (absolute floor 1.0, `NaN` agreeing only with `NaN`) — sized to absorb transport re-encoding without masking real divergence; a failed field read is skipped, a communication fault not being divergence evidence. The check pairs a staged image with the checkpoint of the *same* tick — under the pull-per-scan cadence that is the transfer after the staged scan, the stated detection bound — because the field then holds the active's write for the tick the staged image describes; an unmatched staged image is discarded rather than compared against a different tick's field. Mismatch lands the peer in `Diverged`, which `promote` refuses like any unconverged state; the transition — not each recurring mismatch — is journaled once with the compared tick, and a clean same-tick comparison is the resync that clears it.
- **Alternatives considered:** Promoting on checkpoint freshness alone (a checkpoint proves delivery, not that the standby's subsequent scans track — a skewed component diverges the tick after restore); comparing input images only (two peers reading the same field agree on inputs while computing different outputs — the divergence that matters is in what would be written); post-promotion detection (the wrong outputs are already in the field before anyone looks).
- **Consequences:** Promotion gains an evidence gate: the pair reports not just "holds a checkpoint" but "tracks the field". Divergence is a named, journaled, resync-clearing state — a redundancy fault the UI shows as pair health (decision 19), never a plant fault. The per-kind comparison rule keeps the verdict deterministic: same inputs, same comparison, same answer on every run.
- **Affected tickets:** #89 (this record); #88 implements it; relies on #46 and #64; decisions 13, 15, and 19.

### 27. Checkpoint versioning for rolling upgrades

- **Status:** Implemented (#66). The shape #66 was left to fix: `Checkpoint` carries `format_version` — written as `CHECKPOINT_FORMAT_VERSION` (1), absent on pre-versioning checkpoints where serde defaults it to the accepted version 0; `SUPPORTED_FORMAT_VERSIONS` lists every version a restore accepts — and `model_fingerprint`, an `Option<dcs_core::ModelFingerprint>` holding FNV-1a over the canonical model document (`PlantModel::fingerprint`: the hash covers the parsed model's own reserialization, so key order and whitespace cannot perturb it while any semantic difference can). The assembling layer supplies the fingerprint — `dcs-assembly::assemble` stamps it via `Executor::with_model_fingerprint`, and `Executor::restore` takes the restoring model's as an argument — because the executor stays model-agnostic. Restore negotiates before any state applies: an unsupported version is `RestoreError::UnsupportedVersion` carrying the found and supported versions, a fingerprint mismatch is `RestoreError::FingerprintMismatch` carrying both values, and only then do decision 11's structural checks run — the standby's existing rollback leaves the rejected apply a named, recoverable `Degraded`. Implemented basis: the checkpoint contract itself exists — `dcs-runtime::Checkpoint` (`tick`, `components`, `driver`, `outputs`, `internal`) carries a run between executor instances (#21, decision 11), `GET /checkpoint` serves it and a `--standby` instance pulls and applies one per scan (#32, decision 12), and strict structural restore makes every incompatibility a named, recoverable `Degraded` state rather than a silent divergence. The pair-level path is exercised under #133: `crates/dcs-controller/tests/cross_version.rs` runs the scripted two-peer rig with the standby's per-scan `POST /scan` pull pointed at a fixture `GET /checkpoint` endpoint that proxies the active's live document rewritten into the negotiated wire shapes — the version-0 `format_version`-absent shape, an out-of-set version, and a foreign fingerprint — the recorded crafted-checkpoint-through-the-pull-path serving choice (a JSON document, not a `Checkpoint` value, because only the document can express "the field absent"). The version-0 stream converges the standby to `tracking` and the decision-15 switchover completes bumplessly; each refusal surfaces its named `RestoreError` as `degraded` carrying the found and supported versions or both fingerprints, `POST /promote` answers `not_converged`, and the active's run and field writes stay undisturbed.
- **Problem:** The M3/M4 hot-swap replaces a controller with an identical build. M5's lifecycle goal is replacing it with a *different* build — a bug fix, a component kind whose captured `StateMap` vocabulary grew — while the process runs. As implemented, strict restore rejects any skewed vocabulary: correct, but it cannot distinguish "incompatible build" from "transferable evolution", and a new-build standby discovers incompatibility only when its first checkpoint apply fails — there is no negotiation, so the pair's compatibility is unknowable until the transfer is attempted.
- **Chosen approach (implemented):** The checkpoint gains an explicit `version` field under decision 3's convention: a `CHECKPOINT_VERSION` constant, the loader accepting only known versions, a bump on any breaking format change — mirroring `MODEL_VERSION` on the model document. Beside it the checkpoint carries a fingerprint naming what it was captured under — the model identity, hash of the canonical serialized declarations — so compatibility is negotiated at fetch time: a standby rejects an unusable checkpoint before applying it, and the refusal reports through the existing `StandbySync`/`Degraded` surface (decision 19). The rolling-upgrade sequence then composes existing pieces: start the new build as a standby on the same model; if it accepts the checkpoint version and fingerprint it converges and decision-15 promotion/demotion completes the swap; if not, it reports the named incompatibility and the old build keeps running the process untouched.
- **Alternatives considered:** Keeping structural-only validation (every build change then forces a cold restart — the rolling upgrade M5 exists to provide); a negotiation handshake on the monitoring transport before any checkpoint moves (a second protocol beside the artifact it negotiates — versioning the checkpoint itself answers "can you consume this" directly); on-load migration of old checkpoint formats like the model's (premature for transient peer traffic — a version floor plus the strict per-element checks already name every genuine mismatch); loosening restore to tolerate field drift (rejected in decision 11 — quiet divergence).
- **Consequences:** Checkpoint format joins the versioned-contract surface alongside the model document, and the same optional-field discipline applies: additive changes ride the existing version, breaking changes bump it. Compatibility becomes a pre-flight question with a named answer instead of a failed apply. Per-kind `StateMap` vocabularies remain deploy-together wire contract; now the checkpoint says so explicitly.
- **Affected tickets:** #70 (this record); #66 implemented it; relies on #21 (the format) and #32 (the transfer); #87 consumes the fingerprint to distinguish a model revision from a build skew (decision 25); decisions 3, 11, and 12.

### 28. Automatic failover: heartbeat, self-promotion gating, and fencing

- **Status:** Implemented — #65. `Peer` counts consecutive failed checkpoint pulls (`misses`, reset by any produced checkpoint — the active served, so it is alive) against the budget `Peer::with_failover` arms; `failover_due` reports at the budget-th miss and `self_promote` promotes at that scan boundary exactly like a manual request — reporting `promoting` until the first scan under the lifted gate settles `active`. The convergence gate carries over as a proof that must still *stand*: the last applied verdict was `Tracking` — a diverged or rejected apply voids it — and the miss run has not exceeded the budget, so a single transient miss neither promotes nor re-arms, and an `Unsynchronized`, `Diverged`, or over-budget `Degraded` peer reports its named `StandbySync` state on `GET /role` instead of promoting. Fencing is the field's own arbitration: `dcs-sim-net`'s `PlantRequest::ClaimWriter` takes the plant's write-ownership under an opaque owner token — one token per controller instance covers all its attachments — granted unconditionally and held until preempted; once an owner is claimed, `write` answers a non-owner attachment with `IoError::Fenced` and `step` with `PlantError::Fenced`, while reads and plant tooling stay open. Every promotion — manual `promote` or `self_promote` — runs the claim before the gate lifts, refusing with `SwitchError::FieldClaimFailed` when the claim fails. Device kinds arbitrate through `DeviceBackend::claim`: `sim-tcp` installs the plant-server claim, `sim-bus` the device server's (#154 extends the rule to the register protocol — `claim_writer`/`release_writer` with the claim bound to its attachments, released on a holder's disconnect or explicit release so a dead owner frees the field for a promoted peer), and `FanoutDriver::unfenced_field_devices` names any field-facing device that cannot arbitrate — `--auto-promote N` refuses to start a model that has one, leaving manual promotion. `dcs-controller` wires both paced and `--driven` standby loops to count misses per scan cycle and self-promote when due.
- **Problem:** Promotion is operator- or test-triggered only: an active that dies leaves the field unwritten until someone posts `/promote` to the standby — a human in the loop the vision's hot-swap does not assume. Automating takeover needs recorded rules: how active loss is detected and on what cadence, when a standby may promote itself rather than wait, and how a merely *partitioned* old active is prevented from writing the field beside the new one — the fencing or split-brain rule.
- **Chosen approach:** The checkpoint pull is the heartbeat: a successful `GET /checkpoint` is proof of liveness, so no second channel is introduced. Cadence stays the implemented one — one pull per scan cycle — and loss is declared only after a configured budget of consecutive failed transfers: the budget, not the transport, is the new knob, sizing detection time in scan periods. Self-promotion stacks on the existing convergence gate: only a standby whose convergence proof still stands within the budget may promote itself; `Unsynchronized`, `Diverged`, or over-budget `Degraded` verdicts all block. The fencing rule: exactly one peer writes the field (decision 15), and a heartbeat loss is not proof of death — a partitioned active still believes it owns the field. The field is therefore the arbiter: the plant-facing protocol gains a single-writer claim — the plant server grants write ownership to one owner token at a time, so the promoted standby takes it and a still-alive old active's writes fail as `IoError`s instead of doubling the field writes. Where a field kind cannot enforce single-writer, automatic self-promotion is not enabled: the write gate still lifts on the manual path, but unattended takeover stays off — the split-brain risk is a documented deployment constraint, not a silent hole.
- **Alternatives considered:** A separate heartbeat channel (duplicates the liveness signal the checkpoint pull already carries, and can disagree with it — a peer can heartbeat while serving stale checkpoints); promotion on the first failed pull (network jitter becomes a takeover — the miss budget exists to absorb it); unconditional self-promotion after a timeout (split-brain by design: a partitioned active keeps writing); a third arbiter process or quorum (another deployed component M5 does not otherwise need — the shared field is already the natural arbiter).
- **Consequences:** Loss detection, promotion gating, and fencing become recorded, testable semantics instead of operational convention. The heartbeat rides existing machinery — one new configured budget plus one new protocol element (the writer claim). Fencing honesty is the cost: deployments whose field cannot arbitrate single-writer get manual failover only, and the documentation says so.
- **Affected tickets:** #70 (this record); #65 implements it and #154 extends the fencing to the sim-bus register protocol; relies on #32 (checkpoint pull and named transfer failure) and #46 (roles, gate, switch errors); #88 supplies the divergence half of the gate; decisions 12, 13, 15, and 19.

### 29. Device integration as a registered seam

- **Status:** Implemented — the `DriverRegistry` seam exists (#47): model `Device.kind` strings resolve to factories through `resolve_drivers`, producing a `DriverPlan` whose `build` yields a `FanoutDriver` presenting one `IoDriver` over every backend. `DriverRegistry::standard` installs three registrations covering both contribution shapes: the `sim*` prefix (each device's points join the shared local simulated channel map — the `DeviceDriver::Sim` fragment shape), the exact `sim-tcp` kind (a `RemoteDriver` attached to a `dcs-sim-net` `PlantServer` — the `DeviceDriver::Backend` shape with a step hook and an inspect handle, #31), and the exact `sim-scripted` kind (a `ScriptedDriver` replaying a tick-indexed script declared in the device's `parameters` — `Backend` shape, #67). The integration guide documents the path end to end (#71).
- **Problem:** Per the vision, "adding a device" must be model data, not per-layer engineering: declare the device, bind its channels to logical I/O, and obtain driver resolution, wiring checks, diagnostics, checkpoint participation, and monitoring access from the platform. Before #47 the `sim` backend was hard-coded into assembly, so every new device family would have edited the platform itself.
- **Chosen approach (implemented):** The seam is a registered factory `Fn(&DeviceSpec) -> Result<DeviceDriver, DeviceError>` keyed by the model's opaque `kind` string; exact registrations outrank prefix matches, which is how `sim-tcp` and `sim-scripted` route to their own backends while the rest of `sim*` stays local. `DeviceSpec` hands the factory everything the model declared — the device's id and actual kind string, its `parameters` as arbitrary JSON the factory alone validates, its channels, and the `DevicePoint`s model validation already guarantees agree with them. The factory returns `DeviceDriver::Sim(ChannelMap)` to merge into the shared local simulated backend, or `DeviceDriver::Backend { io, step, inspect }` for a self-contained kind — `step` an optional `StepHook` advancing a simulated backend per `FanoutDriver::step`, `inspect` an optional typed handle reaching beyond the `IoDriver` surface (the scripted driver's recorded-write log). Parameter and construction failures are `DeviceError::parameters`/`backend`, surfacing as `AssemblyError`s naming the device before any scan; an unregistered kind is `UnknownDeviceKind`. Cross-backend wiring becomes `FanoutDriver` routes applied at `step`, so one model can split a loop across device kinds.
- **Alternatives considered:** Hard-coded kind dispatch in assembly (the pre-#47 status quo — every device family edits platform code); per-kind fields in the model schema (splits device knowledge between schema and driver, and the schema would grow with every integration); link-time self-registration (rejected for components in decision 6 — kinds silently absent when unlinked — and the same reasoning applies to devices); driver kinds selected by `io_point` rather than by `Device` (points would carry transport detail — the device is the unit the model already declares).
- **Consequences:** "Adding a device" is: implement `IoDriver`, write the factory, register the kind — resolution, wiring checks, assembly-time error naming, `capture_state` participation (decision 13's per-kind choice), `step`/`inspect` hooks, and monitoring all arrive from the shared layers. The two contribution shapes are both proven: `sim*` merges, `sim-tcp`/`sim-scripted` stand alone. A real fieldbus kind follows the identical path — the seam does not distinguish simulated from physical backends, per decision 5.
- **Affected tickets:** #70 (this record); #47 implemented the registry, #31 the remote kind, #67 the scripted kind, #71 the guide; relies on #19 (the assembly seam) and decisions 5 and 6.

### 30. Plant-side simulation tooling outside the operator contract

- **Status:** Implemented — fault injection and explicit stepping live on the plant side, never on the operator surface: `SimDriver` carries `inject_fault`/`clear_fault`/`step` beside its `IoDriver` impl (#8); the `dcs-sim-net` plant protocol serves `step`, `inject_fault`, `clear_fault`, and `list_points` next to read/write (#31); `dcs-plant-ctl` exercises them as a command-line tool (#68); `dcs-plant-server` runs the shared plant as a process with `--dynamics` declarations merged beside the model (#81, decision 24); and `sim-scripted` replays declared tick-indexed field behavior from device parameters (#67).
- **Problem:** Developing, testing, and demonstrating the system requires perturbing the *world*, not the controller: inject a sensor fault, force a field input, advance plant time, replay a scenario. These are testbench actions on the simulated plant. Routing them through the operator `Command` path would corrupt the operator contract — a fault is the world misbehaving, not an operator action; it should not produce a command receipt, occupy the writability surface (decision 18), or read as an operator entry in the journal.
- **Chosen approach (implemented):** Plant-side tooling addresses the plant, not the controller. `dcs-plant-ctl` speaks the plant server's wire protocol directly — one subcommand per `PlantRequest` — and tests and rigs call the same `SimDriver` API in process. The controller observes only effects through the `IoDriver` boundary: an injected quality fault arrives as an `Uncertain`/`Bad` sample, an error fault as the point's `IoError` — indistinguishable from a real field fault, which is the point. Stepping is explicit and owned: the field-owning peer steps the shared plant once per scan and a standby never does, so plant time advances exactly once per scan regardless of pair membership (implemented in `dcs-controller`'s step closure consulting `owns_field`). Injected faults are part of the simulated plant's state: `SimDriver`'s checkpoint section carries them (decision 13), so a local-sim standby's tracking copy faults identically. Scripts and dynamics are declared device parameters and standalone documents — never `PlantModel` schema (decision 24's boundary).
- **Alternatives considered:** Fault injection through the `Command`/receipt path (corrupts the operator contract with testbench actions and would have to reach through the controller to a plant it does not own); scenario-driving only inside test code (no live demonstration or ad-hoc perturbation of a running pair — `dcs-plant-ctl` exists precisely for that); a private test-only protocol for the plant (blocks the standalone `dcs-plant-server` deployment shape and the second-controller-observes-same-plant property M3 needs); implicit plant time (a plant that advances on its own wall clock reintroduces the nondeterminism decision 4 excludes).
- **Consequences:** Two deliberately separate surfaces result: the operator contract (`Command`/`Receipt`, journal, role endpoints) stays clean of simulation concerns, while the plant protocol is a documented development surface — the monitoring page never offers fault injection because it is not an operator capability. The tooling composes with redundancy and determinism rather than bypassing them: faults checkpoint with driver state, stepping follows field ownership, and scripted scenarios replay identically on every run.
- **Affected tickets:** #70 (this record); #8, #31, #67, #68, and #81 implemented the surfaces; decisions 4, 13, and 24 supply the determinism, checkpoint, and declared-dynamics boundaries.

### 31. Typed model composition

- **Status:** Implemented (#112): the `dcs-build` crate carries the seam — `PlantBuilder` emitting exactly the versioned `PlantModel` document `dcs-model` loads, the per-kind specs in `dcs_build::specs` declaring each kind's string, typed port handles, and parameter set as data, `connect`/`bind` checking port direction and `ValueKind` at compile time through the typed handles, and `build()` reporting named errors for what types cannot carry; `dcs-blocks/tests/spec_drift.rs` pins the specs to the registered kinds' `describe()` output and `dcs-build/tests/tank_loop.rs` reproduces the checked-in tank-loop fixture. Implemented basis: the artifact being composed is already a plain serde document — `PlantModel`'s sections are public fields `PlantModel::validate` checks whether the model arrived as JSON or was built programmatically (#7, decision 3); every registered component kind already publishes its surface as a `ComponentDescriptor` — kind string, port names with direction and `ValueKind`, parameter names with kinds and ranges (#50, #61, decision 16) — and `dcs-assembly`'s `ComponentRegistry` resolves kind strings to constructors (#19, decision 6). Nothing emits a model from Rust today: composition is a hand-written or tool-written JSON document whose port names, directions, value kinds, required parameters, and channel references are all checked only at load.
- **Problem:** The vision asks that an engineer compose plant software in Rust with the contracts expressed through types and enforced at compile time as far as possible. As implemented, a typo'd port name, a `Float` port wired to a `Bool` point, or a missing required parameter is a `ValidationError`/`AssemblyError` discovered when the document loads — never a compile error — and every model edit round-trips through JSON even when the author is writing Rust anyway.
- **Chosen approach (implemented):** A new workspace crate `dcs-build`, depending on `dcs-core` and `dcs-model` only — never `dcs-blocks` or `dcs-runtime`, so the seam stays a model producer with no runtime entanglement. Two halves: per-kind *specs* and a *model builder*. A spec is a data struct per registered kind — declared beside the kind's descriptor vocabulary — carrying its kind string, its named ports as typed handles (name, direction, `ValueKind`), and its parameter set; registering a component from its spec returns an instance whose ports are typed references, and `connect`/`bind` calls check the endpoints' direction and value kind at compile time where the kind is statically known. What types cannot express — resolvable ids, required parameters, channel references — `build()` checks and reports as named errors naming the offending element. `build()` emits the identical versioned `PlantModel` document `dcs-model` loads: the builder is a producer of the one contract, not a second schema, and `validate` remains the backstop for graph-level rules. Because specs are data kept in sync with the registered kinds' descriptors by convention, a checked drift test comparing specs against each kind's `describe()` output is part of the seam, and a worked example reproduces the checked-in tank-loop model.
- **Alternatives considered:** A builder API inside `dcs-model` (the schema crate is deliberately serialization-plus-validation only — decision 6 keeps `dcs-model` free of runtime knowledge, and per-kind spec data is kind knowledge; a separate crate also keeps `dcs-model` small for non-Rust tooling that only parses the document); having `dcs-blocks` kinds emit builders themselves (adds a `dcs-model` dependency to the component library and couples every kind crate to the document format — spec data in `dcs-build` keeps the dependency direction one-way); a proc-macro or external DSL (more machinery than the problem needs — ordinary generics and typed handles already carry the compile-time checks); building documents with `serde_json::json!` (the de facto route tests use today — no checks beyond load-time validation).
- **Consequences:** Two authoring surfaces produce one artifact: a Rust-composed plant serde-roundtrips, loads, validates, and assembles identically to a hand-written document, so versioning, diffs, and tooling are unchanged. Compile-time enforcement covers port existence, direction, and value kind — the checks types can carry; everything else stays a named build-time or validation error, and the boundary between the two is explicit in the spec's types. Spec-versus-descriptor drift is the standing cost: a kind that evolves without its spec is caught by the drift test, and a kind with no spec fails `build()` by name rather than silently compiling a weaker check.
- **Affected tickets:** #104 (this record); #112 implements it; relies on #7 (the document), #19 (the registry the emitted model feeds), and #50/#61 (descriptors as the spec's source of truth); decisions 3, 6, and 16.

### 32. A register-mapped fieldbus device kind

- **Status:** Implemented (#113): `dcs-sim-bus` serves a `RegisterBank` over a length-prefixed binary TCP protocol — per-register read and write, `list_registers`, and an explicit `step` advancing the bank's logical tick — `BusDriver` implements `IoDriver` translating each `PointId` through its channel's declared register and mapping the wire's error vocabulary onto `IoError` (`UnknownPoint`, `TypeMismatch`, `Disconnected`, `Timeout`), `dcs-sim-bus-device` is the device-server binary, `SIM_BUS_KIND` registers in `DriverRegistry::standard` with `DeviceParameters` declaring the server address and each channel's register index — the first kind where `DeviceSpec.channels`/`parameters` do real addressing work — and the `field_facing` backend contributes its `StepHook` and `None` capture under `FanoutDriver` beside `sim`, `sim-tcp`, and `sim-scripted` (the `mixed_bus.json` fixture proves the mixed-kind fan-out). It was built on implemented machinery: the `IoDriver` boundary (#6, decision 5), the `DriverRegistry`/`DeviceSpec`/`DeviceBackend` seam (#47, decision 29), the one remote transport — `dcs-sim-net`'s `PlantServer`/`RemoteDriver` (#31) — `FanoutDriver` routing with `StepHook` and `field_facing` (#47, #64), and explicit, field-owned stepping (decision 30).
- **Problem:** The hardware-abstraction claim — the same component runs against any field interface unchanged — is so far exercised by exactly one remote transport, and it is a friendly one: the `dcs-sim-net` plant protocol addresses `PointId`s in the controller's own logical space and carries `IoError`s verbatim, so it validates the seam's mechanics without stress-testing the translation a real fieldbus needs. A real field interface is register-mapped: device-local numeric addresses, polled or batched exchanges, and a bus-level failure vocabulary. A second transport shaped that way is what proves the boundary is a boundary.
- **Chosen approach (implemented):** A new workspace crate `dcs-sim-bus` carrying a documented register-mapped wire protocol over TCP — deliberately distinct from the line-JSON plant protocol — a `BusDriver` implementing `IoDriver` against a device server, the server binary for integration rigs, and a `sim-bus` device kind registered in `DriverRegistry` so one model mixes `sim`, `sim-tcp`, `sim-scripted`, and `sim-bus` channels under `FanoutDriver`. The three places it differs from `sim-tcp`, and what stays shared:
  - *Addressing.* `sim-tcp`'s wire speaks `PointId`s: the plant server is configured with the model's own point ids and the factory merely probes that each declared point is served — `DeviceSpec.channels` is effectively nominal there. A `sim-bus` device's `parameters` carry real addressing: the server endpoint plus each declared channel's register index — the first kind where `DeviceSpec.channels`/`parameters` do addressing work the model guarantees the shape of and the factory validates. The `IoDriver` surface stays `PointId`/`Value`; the driver translates point → channel → register internally, and a malformed register map is `DeviceError::Parameters` surfacing as `AssemblyError::InvalidDeviceParameters` naming the device.
  - *Error mapping.* The plant protocol returns the server's own `IoError` (`PlantError::Io`) because the remote is itself a `SimDriver`; transport failures collapse to `Disconnected`/`Timeout` at the requesting point. A register bus has its own failure vocabulary the driver owns the mapping for: no answer → `Timeout`, dead link → `Disconnected`, an unmapped register → `UnknownPoint`, a kind- or width-mismatched write → `TypeMismatch`. Polled register ranges mean one failed exchange faults every point the poll covered — each covered point reports the same named failure, and transport-level health reports through the optional `IoDriver::diagnostics` hook (#83), so a dead bus reads as link degradation, not scattered per-point faults.
  - *Step ownership.* Identical rule to `sim-tcp`: the register file is the shared field — server-side state, not the driver's — so the backend is `field_facing: true`, contributes a `StepHook` forwarding `step(dt)` to the device server, leaves `capture_state` at its `None` default (a standby observes the actual registers, per decision 13), and is stepped once per scan by the field-owning peer while `FanoutDriver::step_local` leaves its clock alone on a tracking peer (decision 30). What stays shared through the boundary is everything decision 5 promises: `read`/`write` over `PointId` with declared-kind checks, the `DeviceBackend` contribution shape, write-gate quiescing of field-facing points, fan-out routing, and assembly-time error naming.
- **Alternatives considered:** Extending the plant protocol with register operations (one protocol serving two address shapes proves nothing about foreign transports — the seam's value is that the second kind needs no contract change); encoding register addresses in channel names (loses the validated, kind-checked parameter surface `DeviceSpec` already provides); a controller-local register image stepped like a `sim` backend (`field_facing: false` — a loopback, not a transport; the field-observing shape is what exercises the redundancy and step-ownership semantics); a per-point request protocol like the plant's (misses the batch-failure semantics a polled bus actually has — the mapping must account for one failed poll faulting a whole range).
- **Consequences:** Device `parameters` become the documented addressing contract for real transports — opaque to the schema, validated by the kind's factory at assembly, naming the device on failure. Components and the executor cannot distinguish `sim-bus` from `sim-tcp` except through diagnostics — which is precisely the property the milestone exists to demonstrate. A second `field_facing` kind also exercises the write gate, `step_local`, and fan-out routing under a genuinely shared field rather than a single-remote shape.
- **Affected tickets:** #104 (this record); #113 implements it; relies on #31 (the first transport), #47 (the registry and fan-out), and #64 (field-ownership rules); #83 supplies the diagnostics hook it reports link health through; decisions 5, 13, 29, and 30.

### 33. Alarm acknowledgment

- **Status:** Implemented (#109, filed under M6): the `latching-alarm` kind declares `in` (`Float`, `In`), `ack` (`Bool`, `In`), `alarm` (`Bool`, `Out` — the standing limit state under `AlarmMonitor`'s hysteresis rule exactly), and `unacknowledged` (`Bool`, `Out` — latched on a fresh trip, cleared on every scan `ack` reads `true`, never clearing `alarm` itself); the model wires a writable channel-less `In` point to `ack` so acknowledgment rides the ordinary receipted `WriteValue` path and journals as `CommandSettled`, and the latch rides `capture_state` as `unacknowledged` so a tracking standby inherits it. Implemented basis: `AlarmMonitor` (#22) is strictly auto-clearing — its `alarm` output follows the documented hysteresis rule and carries no notion of operator awareness; channel-less internal `In` points hold operator values and accept `Command::WriteValue` at the scan boundary through the receipt-answered path (#30, #20, decisions 14 and 7); the `writable` flag narrowing that surface to model-declared `In` points is implemented (#49, decision 18); and the journal already records settled receipts and point quality transitions (#35, decision 17).
- **Problem:** Auto-clear alarms answer "is the process outside limits now" but not "did anyone see it": a transient excursion trips and clears before an operator looks, leaving no acknowledged record in history or journal. The missing vocabulary is the standard two-flag alarm model — a *standing* indication reporting process truth plus a *latched* unacknowledged flag reporting operator visibility — and a recorded answer to where the acknowledge action rides: a declared `ack` input the model wires, or a dedicated `Command` variant.
- **Chosen approach (implemented):** Latching is per-kind declared behavior, not a mode of the existing kind: `alarm-monitor` keeps its auto-clear semantics and a sibling latching kind (#109) declares `in` (`Float`, `In`), `ack` (`Bool`, `In`), `alarm` (`Bool`, `Out` — the standing limit state, following `AlarmMonitor`'s hysteresis rule exactly), and `unacknowledged` (`Bool`, `Out` — set when the limit state trips, held until acknowledged). The ack rides the path already built for operator values: the model wires a channel-less `In` point declared `writable` (decision 18, #49) to the `ack` port, and the operator acknowledges with `Command::WriteValue` on that point — a writable internal point holds the written value until the next command, which is what makes the level-observed ack below well-defined. No new `Command` variant and no new `Component` hook: an ack is an operator value like a setpoint (decision 14), so it inherits the receipt contract, the writability surface, telemetry visibility, and checkpoint carryover through the `internal` section for free. `ack` is level-observed like every input: while it reads `true` the `unacknowledged` latch releases — a standing alarm then reads as acknowledged-but-active, which is the two-flag model's point — and a fresh trip after the latch cleared re-asserts it; the kind documents its precise edge cases per #109's convention. Journaled: the ack write settles as `JournalEvent::CommandSettled` naming the ack point — the identical audit every operator action gets — while `unacknowledged` and `alarm` transitions appear in the points' history streams; no dedicated alarm event type is added. The latch is run state: `capture_state` carries it so a tracking standby inherits unacknowledged alarms — decision 20's checkpoint obligation applied to latched state.
- **Alternatives considered:** A dedicated `Command::Acknowledge { component }` variant with a `Component::acknowledge` hook (a component-targeted command carrying an empty payload — it duplicates what a point write expresses, needs a new hook plus a journal event to stay as auditable, and names only a component, so a kind raising several alarms could not say which was acked); auto-clear as the only behavior (loses the operator-visibility record entirely — a transient alarm leaves no trace it stood); making `alarm` itself latch until ack (conflates the two flags — the standing indication would report operator state, not process truth); edge-triggered ack requiring the component to observe the `false`→`true` transition (workable, but level semantics make a checkpoint-restored `ack` point's meaning obvious — `true` means the acknowledgment is held).
- **Consequences:** Acknowledgment needs no contract extension — a model-declared point, an ordinary command, a journaled receipt — and the page's ack affordance is a writable-point edit like any other, so #108's alarm summary pane consumes `alarm` and `unacknowledged` as ordinary status-role ports. The two-flag split keeps process truth and operator acknowledgment independently visible in telemetry, history, and checkpoints. The `writable` mark makes the ack surface explicit model data: an unmarked `In` point rejects `WriteValue` with `CommandError::NotWritable`, so the ack affordance exists only where the model declares it.
- **Affected tickets:** #104 (this record); #109 implements the latching kind; relies on #22 (the auto-clear baseline), #30 (internal points), and #20 (the command path); #49 supplies the writable surface; #108 consumes the flags; decisions 7, 14, 17, 18, and 20.

### 35. Checkpoint persistence for restart recovery

- **Status:** Implemented (#115): `dcs-controller --state-file PATH` writes the serde `Checkpoint` — the same versioned, fingerprinted contract `GET /checkpoint` serves (decisions 11, 27) — at the end of every completed scan cycle, after the scan and the plant step, by write-then-rename to a sibling `PATH.tmp`. When `PATH` exists at startup the run resumes: the checkpoint is applied in place to the freshly assembled executor (`Executor::apply`) before pacing begins; a missing file is a cold start. Every resume failure — unreadable or unparseable file, unsupported format version, fingerprint or structural mismatch — exits nonzero naming the file and the reason.
- **Problem:** The checkpoint machinery moves a run between *peers* (decisions 11–13): a lone controller restart has no standby to converge from and would cold-start, interrupting the process the vision wants uninterrupted. The checkpoint format already carries everything a continuation needs — tick, component state, image, and driver-side state (decision 13) — so persisting it locally is the no-peer recovery story.
- **Chosen approach (implemented):** Reuse the one checkpoint contract rather than a second persistence format: the file holds exactly the JSON `Checkpoint` a standby pulls, so the negotiation a peer performs — `format_version` against `SUPPORTED_FORMAT_VERSIONS`, `model_fingerprint` equality, then decision 11's structural checks — is the same negotiation a restart performs, with the same named failures. The recorded boundary is the end of each scan cycle, after `step` has run: the checkpoint then captures the post-step driver state the next scan's input phase reads, so a resumed run re-enters the loop at the point the capture was taken — writing mid-cycle would resume with the driver one step behind. Writes are atomic (temporary sibling plus rename) so a crash mid-write cannot leave a torn file that a later resume must reject. Resume is automatic on the file's presence — no separate flag — because the flag's purpose is recovery: a restarted process given the same command line resumes, while a missing file is an unambiguous cold start. Restore is all-or-nothing per decision 11: a version or fingerprint mismatch, a corrupt file, or a changed model exits nonzero naming the reason rather than silently starting fresh — a state file that exists but cannot be resumed is a fault to surface, never a hint to ignore. The choice also extends to the `--driven` mode, where the write rides the per-requested-scan `after_scan` hook — now receiving the `Peer` — at the same end-of-cycle boundary.
- **Alternatives considered:** A separate `--resume` flag instead of resume-on-existence (a restarted process would need its command line changed to recover, and a stale `--resume` with no file is its own failure mode — existence is the honest signal); checkpointing every N scans or only on each checkpoint the monitor serves (both leave the persisted state behind the run by a configurable or request-driven amount — every cycle is the simplest boundary that loses at most the in-flight cycle); a bespoke run-state document instead of the `Checkpoint` (a second versioned contract to keep compatible with restore semantics forever).
- **Consequences:** Restart recovery needs no peer: the process dies, restarts with the same arguments, and continues at the last completed cycle — determinism makes the continuation identical to the uninterrupted run. The standby path is unchanged and remains the preferred recovery where redundancy exists: a tracking peer converges continuously and takes over without a restart, while the state file resumes only from the last persisted cycle after the process has died. What the checkpoint does not carry — receipt history, I/O-health counters, journal and history buffers — restarts fresh; the file recovers the run, not its diagnostics. A state file is bound to its model by fingerprint: a changed model fails resume by name, per the all-or-nothing rule.
- **Affected tickets:** #115 implemented it; relies on #21 (the checkpoint contract and all-or-nothing restore), #66 (version and fingerprint negotiation), and #64 (the driven-mode scan boundary); decisions 11, 12, 13, and 27.

### 36. Journal persistence beyond restart

- **Status:** Implemented (#163): `MonitorConfig::journal_file` — wired on the controller as `--journal-file PATH`, requiring `--listen` since the recorder lives in the monitor — appends every journaled entry to `PATH` as a line-delimited `{"entry":{...JournalEntry...}}` record at the recorder's documented point, replays the file at bind to seed the ring and continue `seq` numbering, and opens each process lifetime with a `{"run_boundary":{"run":N,"tick":T}}` marker — `tick` recording the tick the run starts at, so a `--state-file` resume's restored tick domain is visible in the file. A record that cannot be replayed fails startup naming the file, the line, and the offending record; a missing file is a cold start; an append the file cannot take is fatal rather than a silent gap in the audit trail. Implemented basis: `dcs-monitor`'s `Recorder` already appends to the bounded per-point history rings and the transition journal once per completed scan — the documented recording point after the write phase, never mid-scan — with oldest-first eviction and never-reused `seq`s making eviction visible (#35, decision 17); `JournalEntry`/`JournalEvent`/`HistorySample` are serde contract types served over `GET /journal` and `GET /history`; and the checkpoint state file (#115, decision 35) gives a lone controller restart its resume story — its consequence section naming exactly this gap: "the file recovers the run, not its diagnostics". Point history remains volatile per decision 17; only the journal persists.
- **Problem:** The journal is the run's audit record — settled commands, quality transitions, step failures, role changes, divergence verdicts — and it lives only in the bounded in-memory ring. A controller restart drops it: the operator-action trail the receipts and journal exist to provide (decisions 7, 17) resets with the process, and a post-incident review of who commanded what cannot reach back across a restart. Decision 35's checkpoint file resumes the run's *state*; nothing preserves the run's *record*.
- **Chosen approach (implemented):** A file-backed journal sink as monitor-local tooling, not a contract concern. When a path is configured on the controller or monitor, every entry the `Recorder` appends to the transition journal is also appended to a line-delimited JSON file at the same recording point — after the write phase, under the monitor lock, never mid-scan. On startup the monitor replays the file to seed the in-memory ring and continue `seq` numbering where it left off, so `GET /journal` answers continuously across a restart and a consumer still sees a retained gap as a numbering gap. The file reuses the contract's serde serialization but is the monitor's own format — its readers are tooling and the replaying monitor itself, not contract consumers — and a run-boundary marker record distinguishes process lifetimes in one file. Point *history* stays volatile per decision 17's original reasoning: it is high-volume diagnostics that re-accumulates after a restart, where the journal is the low-volume record that cannot be reconstructed. Interaction with decision 35's state file: the two are deliberately separate — the checkpoint file is state to resume a run, overwritten per save and consumed by restore; the journal file is the append-only record of what happened, consumed by review. A run resumed through `--state-file` continues appending to the same journal file in the restored tick domain, so the audit record spans the restart the state file healed.
- **Alternatives considered:** Persistence as contract — a `JournalSink` trait or mandated file schema in `dcs-core` (elevates an operations tool to wire contract every consumer must version, for a payload that is already contract-serialized); folding the journal into the checkpoint file (conflates resumable state with audit record — the checkpoint's overwrite-per-save shape fights append-only history, and a standby pulling checkpoints would drag a growing record); an embedded database or external log shipper (operational machinery the single-binary deployment does not otherwise need); persisting history samples too (volume and re-accumulation argue against it — the ring is a diagnostic window, not an archive).
- **Consequences:** The audit record survives restarts with no contract churn: endpoints, event types, and payloads are unchanged, and the ring stays memory-bounded while the file is the durable tail — file growth is a deployment-managed bound, not the contract's. Determinism is unaffected since appends ride the existing recording point. The choice is reversible: because the file serializes contract types, a later contract-level persistence story can adopt the same payloads.
- **Affected tickets:** #137 (this record); #163 implements it; interacts with #115/decision 35 (the sibling persistence surface, implemented); relies on #35 (the recorded streams) and decisions 7, 8, and 17.

### 39. Command-path audit identity

- **Status:** Proposed — the implementation ticket is filed under M8. Implemented basis: every submitted `Command` settles into exactly one `CommandReceipt` — echoed command plus outcome (#20, decision 7) — journaled as `JournalEvent::CommandSettled` carrying that receipt (#35, decision 17). The journal is thus already the ordered audit surface for operator actions; it lacks only *who*.
- **Problem:** The vision names safety-related constraints among the platform's encapsulated concerns, and audit's first element is actor identity: the journal records that a setpoint moved at a tick but not who asked. `POST /command` is anonymous as implemented — a receipt cannot distinguish one console's write from another's, and the durable journal of decision 36 would preserve an unattributed record.

The page sources the identity from configuration — an operator name in the page's URL parameters or a page-side entry — and includes it on every submission; an absent actor journals as unattributed rather than rejected. Recorded honestly: this is *declared* identity — attestation, not authentication. The simulated transport has no auth layer; verifying an actor is deployment machinery (a fronting proxy or gateway) the contract deliberately does not prescribe. The field still earns its place: it makes attribution part of the receipt-answered contract, journaled at the scan boundary like every other audit entry, and a deployment that fronts the monitor can fill it from authenticated context without a contract change.
- **Alternatives considered:** An authenticated transport first (identity without verification is weaker — but authentication is a cross-cutting deployment concern: folding it into the command contract now couples the audit record to a mechanism the simulated system cannot exercise, while declared identity leaves the seam exactly where a deployment needs it); a separate audit API beside the journal (splits the run's ordered record — attribution belongs on the settled receipt the journal already carries); `actor` on `Command` itself (the enum's externally-tagged serde shape gains the field awkwardly, and identity is submission metadata — about who sent it, not part of the operation the executor applies); per-endpoint tokens mapped to identities (authentication by another name — the same deferral).
- **Consequences:** The audit trail gains attribution with no new event types, endpoints, or required fields — an old client's commands journal exactly as before, actorless. Checkpoint and peer traffic are unaffected: the actor lives on the submission and receipt path, not in executor state. The honest limit is recorded: until an authenticating front exists, actor strings are operator-declared and the journal proves *what was claimed*, not *who truly sent it* — sufficient for the simulated system and the documented extension point for a hardened deployment.
- **Affected tickets:** #137 (this record); the M8 audit-identity ticket implements it; relies on #20 (receipts), #35 (the journal), and the M8 journal-persistence ticket (the record it attributes); decisions 7, 8, and 17.

### 40. JSON Schema for the plant-model document

- **Status:** Accepted and implemented (#159): `dcs-model schema` prints the draft 2020-12 JSON Schema `PlantModel::json_schema` emits, and `crates/dcs-model/tests/schema.rs` sweeps the checked fixture corpus against it.
- **Problem:** Decision 3 chose JSON so non-Rust tooling can read the model, but nothing external could check a document without linking the Rust validator. The model is the shared contract, so its checkable surface should travel with the document format, not only with `PlantModel::load`.
- **Chosen approach (implemented):** The schema is *emitted as data* — a hand-maintained document in `dcs-model`'s `schema` module, not generated from the serde types (e.g. via `schemars`). Hand authorship is deliberate: the schema intentionally diverges from deserialization in both directions, and deriving it from the types would lose the divergences that make it useful. The schema is *stricter* than serde where that serves engineering: `additionalProperties: false` everywhere (serde silently ignores unknown keys, so a misspelled field would evaporate), `version` as a `const` stamped from `MODEL_VERSION`, and `uniqueItems` on the four id-keyed collections (a sound approximation of id uniqueness — identical elements necessarily share an id, so nothing valid is rejected). It also expresses the intra-element rules `validate` owns but the type shape alone does not: an internal point's required `initial`, the bound-point ban on `initial`, `initial`'s variant matching `value_type`, and `writable` restricted to `In` points — plus the standard registry's known device-kind parameter shapes where conditional (`if`/`then`) subschemas can write them down: `sim-tcp`'s `address`/`timeout_ms`, `sim-bus`'s `registers` map, and `sim-scripted`'s `script` entries. `Option` fields admit `null`, matching serde. The drift check runs every checked-in `*.json` fixture through the emitted schema with a dev-dependency validator (the `jsonschema` crate): valid model documents — including their serde re-serializations — must pass, non-model documents must fail, and every `invalid/` fixture carries a pinned per-layer verdict so a schema or validator change flips a checked expectation instead of drifting silently.
- **Alternatives considered:** Generating the schema from the serde types (schema-on-derive cannot express the conditional intra-element rules, would mirror serde's silent unknown-key acceptance, and adds a derive dependency to `dcs-model` and `dcs-core` — rejected); a checked-in `.schema.json` file the CLI prints verbatim (equivalent, but the embedded document keeps `MODEL_VERSION` stamped from code and one canonical source; external tools fetch it through the subcommand); encoding the `sim*` prefix family's no-parameters rule (rejected — the open prefix cannot be pinned per-kind, and a checked-in valid document carries `sim*` parameters the standard factory would reject only at assembly, proving the constraint is not document-shaped).
- **Consequences:** What the schema cannot express is recorded rather than implied: cross-reference checks (channel bindings, signal `source`, connection endpoints naming declared elements), wiring checks (`from` produces / `to` consumes / kinds agree — they depend on the *referenced* element's declarations), general id uniqueness beyond identical elements, the semantic halves of the device-kind contracts (resolvable addresses, register-map coverage and uniqueness, script channel binding and tick ordering, script values matching channel kinds), and JSON's integer/float lexical distinction (schema compares numbers mathematically, so `1.0` passes an integer field serde rejects). Those stay with `load` and the assembly factories: the schema is a first screen for external tooling, not a replacement validator — a document passing it may still fail `PlantModel::load`, and the schema in turn rejects some documents `load` accepts (unknown keys, malformed known-kind parameters). The known-kind parameter sections encode the *standard* registry's contract; a deployment registering other device kinds extends or regenerates them.
- **Affected tickets:** #159 (this record and implementation); decision 3 (the serialization contract it describes); decision 29 (the device-kind seam whose parameter shapes it mirrors).

### 41. Declared input freshness budgets

- **Status:** Accepted and implemented (#196): `io_point` declarations carry an optional `stale_after_ticks`, the point map rides it into the executor, and the input phase stamps `Uncertain(Stale)` once a field input's driver-stamped sample tick lags the scan tick past the budget.
- **Problem:** WW-OPS-003 asks operators and control components to distinguish stale data. `QualityReason::Stale` has existed in the contract since the signal model — every quality-propagating kind honors it — but no runtime path produced it: only scripted playback or fault injection could name the reason. A field source that stops refreshing looked exactly like a healthy one, because the executor re-stamps every input read with the scan tick and the last value reads `Good` forever.
- **Chosen approach (implemented):** Freshness is *declared*, not inferred. `stale_after_ticks` is an optional non-negative integer on field `in` `io_point` declarations, following the optional-field convention (`writable`, `channel`): documents predating it load and serialize unchanged, the model version stays 1, and validation confines it to channel-bound `in` points (`StaleOut`, `StaleInternal` elsewhere) — an `out` point is never read and an internal point never reaches a driver, so a budget there could only mislead. Assembly carries the budget onto the field point's `PointSpec`; the executor's input phase consults the *driver-stamped* tick before re-stamping — when `scan_tick - sample_tick` exceeds the budget, the landed quality merges `Uncertain(Stale)` by the worst-of rule, so a driver-reported `Bad` or worse-named `Uncertain` is never improved, and the first in-budget read returns the driver's own quality. The executor remains the only timestamp authority: the image stamp is the scan tick either way, and the driver tick is evidence for the check only — so drivers need no new contract beyond the `Sample::tick` the existing sim, remote, and bus protocols already carry. The transition reaches operators through the existing machinery: the recorder's quality diff journals `QualityChanged` at the scan tick and the page renders the named `stale` reason — no new event, endpoint, or wire type. A driver whose samples carry no usable freshness signal — stamping every read with the current tick, or a fixed tick — makes the declaration inert or always-stale; `docs/model-reference.md` records the rule to declare the field only where the source distinguishes fresh samples from held ones.
- **Alternatives considered:** An executor-side refresh detector watching every field input (no declared budget — a uniform timeout would guess at per-source rates the model knows better, and an undeclared point could never opt out; the declaration also travels with the document reviewers sign off); deriving staleness from wall-clock or scan-period time (ticks are the run's only deterministic clock — wall-clock would break the replayable, identical-runs guarantee the scripted tests pin); a new journal event or wire type for staleness (rejected — the quality-transition path already attributes and renders named reasons, and `Stale` was already a first-class `QualityReason`); drivers marking their own samples stale (the field does not know the consumer's scan cadence — freshness is a contract between the declared budget and the scan tick, which only the executor holds).
- **Consequences:** Field `in` points gain an opt-in freshness contract with no change for undeclared points, failed reads, forced points, or internal points; `PointSpec` carries the budget beside `writable` as point metadata; `dcs-build` composes it through `field_input_stale_after`; and a stale input's transition is journaled, rendered, and checkpoint-neutral like any other quality change — staleness is recomputed from field evidence every scan, never latched.
- **Affected tickets:** #196 (this record and implementation); relies on #5 (the signal model supplying `QualityReason::Stale`), #9 (the executor's input phase and timestamp authority), #83 (the I/O-health surface staleness sits beside), #35 (the quality-transition journal the transition rides), and WW-OPS-003.
