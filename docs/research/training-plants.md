- **Affected requirements:** `WW-FND-001`, `WW-FND-003`, `WW-FND-004`, `WW-ENG-003`, `WW-OPS-001`–`WW-OPS-003`, `WW-CTL-001`, `WW-CTL-002`, `WW-LCM-001`; deployment discussion also touches candidate `WW-LCM-002`.

## Product goal recorded from the discussion

Plant engineers compose equipment, logical I/O, control relationships, site policy, alarms, and operator drawings in typed Rust code. A customer plant depends on versioned platform releases in its own repository. Engineering remains code-based; an engineering UI is outside this direction. The operator UI exposes only the declared operating and tuning capabilities.

Standard equipment should ship with an explicit control contract, a compact reusable symbol, a consistent equipment control panel, and executable acceptance scenarios. Measurements should pair an exact value and unit with quality/freshness and, where configured, a small range indicator or trend. Familiar industrial conventions inform behavior and interaction, while DCS supplies original presentation and its own declared semantics. Standardization supports repeatable operation and tests; determinism additionally depends on scan timing, state transitions, precedence, and fault handling.

The near-term goal is one convincingly connected, fully operable simulated water area using a small complete set of elements. Extend the existing reference station and public consumer proof before expanding the catalogue or creating another reference application. Vendor training breadth does not change the water-first market sequence or authorize batch scope.

## Proposed next steps and measurable completion

1. **Inventory existing contracts before adding kinds.** Map motor/pump, on/off valve, modulating actuator, analog measurement, loop, and alarm to existing library behavior, `BlockInterface` resources, equipment metadata, symbols, and consumer tests. Record missing presentation capabilities separately from missing runtime semantics. The result names what can be reused and the smallest gaps needed by the chosen area.
2. **Specify the area and scenarios in code.** Extend the customer-owned station example through the released engineering seam. Declare equipment, topology, units, initial conditions, ranges, allowed actions, and simulation dynamics; document every simplification and source relationship. Each drawn connection has an actual process meaning, and unrelated demo loops are not connected cosmetically.
3. **Complete the shared operator elements.** Provide original symbols and consistent control panels driven by declared semantic resources, with a generic fallback. Important readings show exact value/unit/quality; optional small bar indicators use explicit display bounds, and normal bands remain distinct from alarm limits. Keep measurement, setpoint, command demand, and actual feedback separate. Do not infer command rights or state meaning from tag spelling. Any additional presentation metadata needs its own reviewed contract proposal, not a second authoritative model.
4. **Prove the combined behavior.** Run scripted normal operation, setpoint changes, manual/auto transitions, blocked starts, failed feedback, bad/stale measurement, warning versus trip, alarm acknowledgment, UI disconnect/reconnect, restart, and compatible controller takeover. The same model/scenario/inputs produce the same authoritative outputs and command outcomes. Review populated screens at desktop and phone sizes, with keyboard navigation and reduced motion, including abnormal states. Reuse the established acceptance harness rather than introducing a parallel UI test framework.
5. **Prove release consumption and record remaining gaps.** A clean external plant checkout builds, validates, simulates, and exposes the declared controls with pinned release artifacts and no DCS workspace dependency. Publish scenario evidence and a capability matrix; expand the catalogue only where this area or accepted water requirements expose a gap. Training evidence does not close customer policy or site commissioning assumptions.

Completion means an engineer can compose the area entirely in code and obtain the standard control/UI behavior without customer JavaScript for each equipment instance. An operator can identify actual state, command availability, blocking cause, measurement confidence, and command settlement while retaining process context. The controller remains authoritative and continues scanning when the UI is absent or slow.

## Deployment direction from the same discussion

**Proposal, not a new architecture decision:** adopt the reviewable plan/apply idea from S8 for plant releases while retaining the existing manifest, fingerprint, checkpoint compatibility, model diff, and active/standby mechanisms. A future deployment plan should name the exact release/model artifacts, parameter and I/O changes, state carryover or reinitialization, online eligibility, required interruption, and recovery procedure. Applying a reviewed plan must reject a changed deployment basis rather than silently applying a different transition.

Infrastructure provisioning may use Terraform where a deployment has suitable providers. Plant activation should be implemented through DCS lifecycle contracts: stage the compatible standby, validate synchronization and ownership, transfer control, and verify the resulting release. Compatibility limits still govern model revisions; not every change can be made online. A Terraform provider would be a later adapter to that workflow, not the place to define the control logic. These tool choices remain open until deployment requirements justify them.

Engineering defaults, persisted operator settings, runtime state, and infrastructure state need explicit ownership. A plan must explain whether an operator-adjusted setpoint is preserved or intentionally replaced. Recovery must account for compatibility with the state produced by the new version; restoring a previous image alone is not proof of rollback. This is research input to candidate `WW-LCM-002`, not a claim that a complete deployment orchestrator or universal rollback already exists.

## Open questions and revisit conditions

- Which motor/valve/loop variants and manual-mode protections does the first operator workflow require? Keep site decisions configurable under the existing station assumptions.
- Which measurements need normal bands, small gauges, or trends, and who owns those limits? Define display context explicitly before implementing new metadata.
- What fidelity is sufficient for the first area? Use original, documented water dynamics; revisit S4 only for a demonstrated interaction-model gap and S5 only for a biological-control requirement.
- Does the next deployment need a platform orchestrator, infrastructure automation, or only the existing manifest/rig procedure? Revisit when a pilot deployment plan names topology, activation, backup, and rollback obligations that current seams cannot express.
- Are external project code or datasets actually needed? Inspect their particular terms and reproducibility before adopting them. Public descriptions are sufficient for this research; external accounts and hardware access are not prerequisites for the first slice.


## Connected-area implementation follow-up — 2026-10-10

The assigned slice uses the recommended S7 station behavior and S3 connected training approach. Its balance vessel/PI discharge topology and all numeric parameters are original simulation engineering, explicitly distinguished from source behavior in the [area record](../milestones/connected-water.md). Existing executor equipment and managed alarm semantics were reused. New evidence includes negative-gain anti-windup, authoritative numeric command bounds, shared display context, physical-versus-sensor separation and the independent candidate-artifact consumer. The existing harness checks normal/fault operations, six consumer schedules, durable restart and paired takeover on the same area. See that record for reproducible commands and remaining release/browser gates. This adds evidence to the water baseline, not a new market or automatic planning authorization.
