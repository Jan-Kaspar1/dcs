# Bulk engineering, templates, naming conventions, and site-specific parameter sets

- **Checked:** 2026-09-15
- **Question:** What do owner specifications, standards, and regulator requirements actually demand of the engineering layer around a control system's plant model — tag and naming conventions the configuration must carry; I/O lists and loop drawings as contractual artifacts and which of them the model must import or export; how owner standards express typicals and templates — repeated equipment modules instantiated per site with site-specific parameters; bulk-editing and bulk-commissioning practice such as parameter sheets and per-tag-class checkout; and the versioning or review evidence owners demand for configuration changes — so that `WW-ENG-002` can carry either observable acceptance criteria or a concrete revisit condition?
- **Affected requirements:** `WW-ENG-002`; edges touch `WW-ENG-001` (reusable plant composition, accepted) and `WW-FND-001` (the one-plant-contract document)

## Supported findings

### Naming and tagging — conventions exist, are mandatory, and diverge

- Water-sector owners publish tag-naming standards the control system must implement, and they cite ISA-5.1 while diverging from each other. Seqwater's tag standard adopts a device-name / optional instance-identifier / descriptor structure that *retains the owner's equipment numbering* and names ANSI/ISA-5.1-2009 among its reference standards [10 Table 5-2, §6]; a county utility fixes a compact format for physical I/O tags and uses PLC-device-ID plus ISA equipment identification for virtual points, with a same-name rule across its several SCADA projects [18 §2.3]; a municipal waterworks built a 12-character fragment system on ISA-5.1 covering not only equipment and I/O but operator setpoints, calculated values, and alarm types [20]; a second county replacement standardized on ISA-5.1 naming after inheriting bare Modbus addresses [26]. What is uniform is the obligation, not the format — each owner's convention is its own.
- Tag identity flows *down* from the owner's asset numbering, not up from the control system: the equipment identifier must propagate into drawings, tag naming, alarms, interlocks, the historian, I/O lists, C&E matrices, functional descriptions, and network diagrams [11], and changes to equipment numbering cascade into control-system tags through the owner's formal change management [10 §6]. The control system's naming is derived data — the owner's asset register is authoritative.
- The standards layer supplies the general machinery the conventions instantiate: ISA-5.1's functional-identification-plus-loop-number scheme [1] with organizational alternatives explicitly permitted [1 scope; 2]; IEC 81346's aspect-based structuring and reference designations, including the *type* aspect that distinguishes an object's type from its occurrences [3 §§4–6]; and IEC 62424's PCE-request reference designations with explicit *typical identification* [4 §§6.3.5–6.3.6] — the exchange standard itself encodes the type/instance distinction.
- A naming convention's reach is broader than field points: owner conventions name virtual points, calculated values, setpoints, and alarms as well [18 §2.3.2; 20]. Any tag support in the model must cover internal and operator points, not only channel-bound I/O.

### Engineering deliverables — I/O lists, loop drawings, functional descriptions

- The I/O list is a named contractual design deliverable with an owner-prescribed form and a lifecycle: Seqwater's design-deliverables clause names the I/O list [12 §7.9.2] and the owner publishes the template it is produced on [13 TEM-00210], keeps it in native spreadsheet form inside the controlled document system [14], and tests the design it documents [17]. Sydney Water's commissioning matrix makes preliminary and revised I/O lists contractual submittals [22]; instrument calibration and configuration at commissioning are performed per the I/O list [23]; and the sector backup guidance names I/O lists among the artifacts a restore needs (`docs/research/deployment-commissioning.md` source 7). The I/O list is simultaneously a design submittal, a build input, a commissioning reference, and a maintained record — it must agree with the running configuration for the asset's life.
- Loop drawings and loop checks are the per-loop verification artifacts: loop diagrams divide each loop into PICS-I/O, panel-face, back-of-panel, and field zones (Port Orange, cited in `docs/research/deployment-commissioning.md`); the loop check is the standardized activity between completed loop construction and cold commissioning, with a generic per-loop check form [8]; point-to-point testing is a named minimum SAT test [17 §12.2]; and owner commissioning practice checks each instrument at 0/25/50/75/100% of span rising and falling [23].
- The surrounding deliverable set is owner-templated: functional descriptions are produced on published Part A/Part B templates and submitted with the C&E matrix and master alarm list [15, 13]; inspection certificates, the alarm database, and the C&E matrix are likewise published template artifacts [13]; and a standard-format function description is excused only when the control system already adheres to a standard template [22].
- What the sources require of the control system's model is *data interchange and consistency*, not document production: the deliverables are owner-format spreadsheets, drawings, and Word-template documents that must agree with the configured system [10–15, 22]. The exchange standard for the diagram side — PCE requests carried between P&ID and control-engineering tools through a neutral CAEX model of the plant hierarchy [4 §7] — shows the industry answer is a defined data exchange, not the control system emitting drawings.

### Typicals and templates — repeated modules with site parameters

- The owner "typical" is a *standard specification applied per asset*, not a per-site design: a control-design standard fixes hierarchical philosophy, equipment control modes, and standard equipment functions for every site [12 §8; 16]; one utility publishes a single standard control narrative instantiated across its whole pumping-station fleet [21]; another publishes per-asset-class standards [24]; a third requires a function description only where a standard template is not adhered to [22]. Site specificity enters as the parameters and composition of standard elements — pump counts, setpoints, instrumentation — not as bespoke behavior.
- Vendor engineering machinery shows the instantiation shape the owner typicals imply: a template chart instantiated in bulk through an import file, with the type approved once and bulk modifications propagated to instances [25]; parameterized tag types whose children self-configure from parent parameters and whose optional members are enabled per configured instance data (pump count) [26]; bulk assignment of control-module types, bulk connection editing, and signal-designation mapping tables [25 §§11.12–13]. The type/instance split with bulk instantiation is how the industry keeps a plant's point count tractable.
- Commissioning is staged per template class in practice: one integrator commissioned a single site per asset type in parallel with the outgoing system, then rolled the validated templates across the fleet [26] — the per-tag-class checkout pattern applied at whole-site scale.

### Bulk editing and bulk commissioning — parameter sheets and per-class checkout

- The industry's bulk-edit surface is the per-class tabular document: ISA-TR20's specification forms organize each device category's parameters on a defined form with picklists [5]; IEC 61987 structures the same data for electronic exchange — operating/measuring-point properties (OLOP) and device properties (DLOP) [6]; and the owner deliverables themselves are spreadsheets — the I/O list kept in native Excel [13, 14], the master alarm database template [13 TEM-00254], the record-drawing and O&M indices [19]. Parameter sheets are how bulk data is authored, submitted, reviewed, and maintained.
- Bulk modification in the engineering tools is type-keyed: updating the process tag type and reimporting propagates changes to all instances [25]; parameter expressions propagate parent values to children in the tag-type model [26]; mapping-table templates assign signal designations in bulk [25 §13].
- Bulk commissioning is per-class, not per-point-unique: per-instrument loop checks at fixed span fractions [23], point-to-point testing across the I/O list [17], C&E-matrix-driven testing [15, 17], and per-alarm inspection certificates from a template [13 TEM-00212] — each a repeated check parameterized by tag class.

### Versioning and review evidence for configuration changes

- Engineering data is configuration-managed as *documents*: controlled storage in native plus PDF form with a document coordinator releasing revisions, per-document registers carrying check-out details, and downloads/prints becoming uncontrolled [14]; functional-description changes run through the same maintenance procedure [15]; and equipment-numbering changes that would rename tags require formal change management [10 §6]. The versioning evidence owners demand is document control over the deliverable set — revision registers, approvals, controlled distribution.
- Regulator and owner review is milestone-shaped: construction approval requires final detailed plans and specifications approved by the reviewing authority [9 §10.2, Ch. 20]; commissioning hold points gate design and commissioning-plan approval [23]; the submittal matrix requires preliminary and revised I/O lists [22]; and handover demands work-as-constructed records transmitted under naming conventions and indexed registers [19, 22].
- Alarm configuration is the one area with a standards-defined change process on the control data itself: alarm-system changes pass management of change, and the rationalized alarm set is maintained in a master alarm database [7 §17, §§8–9; 13 TEM-00254].
- Testing evidence reviews the *effect* of change, not the edit: witnessed FAT/SAT, point-to-point results, and signed-off reports verify the configured system against its design artefacts [8, 17, 23] — the deliverable documents are the baseline the test record is judged against.

## Existing seams versus contract gaps

What the implemented seams already express, needing no contract work:

- **The versioned model document as the engineering artifact.** The `version`-stamped `PlantModel` document with load-time validation (decision 3), the emitted JSON Schema (#159, decision 40), and `dcs-controller --check` (#160) already make the configuration a controlled-document-shaped artifact that owner document control applies to [14]: `dcs-model diff` (#114) is the revision-review surface, and the advisory `dcs-model lint` (#136) is the engineering-quality pre-submittal check the deliverable workflow implies.
- **Typed composition as the template mechanism.** `dcs-build`'s spec/instance split (decision 31, #112) is the type/instance machinery the sources describe [3, 4, 25, 26]: a per-kind spec is the approved-once type, `PlantBuilder::add` instantiates, `connect`/`bind` enforce direction and value kind at compile time where the types reach, and `build()` emits the versioned document with named errors for what types cannot carry. Composition is deterministic — the declared point-id block scheme in `station.rs` emits identical documents for identical configurations, which is itself a naming/addressing convention generated *by* the template rather than maintained beside it.
- **The station helper as the site-specific parameter set.** `pumping_station(PumpStationConfig)` (#220) is the typical-plus-parameters pattern in code: one config struct — pump count, the ordered setpoint table, rotation policy, delay budgets, fault and hysteresis values — instantiates the whole station (measurement failover, threshold chain, pump group, per-pump mode and availability wiring, the full alarm set, operator points), and `PumpStationLayout` reports where every declared id landed — the index an I/O list would be generated from.
- **Signal and display metadata.** `Signal::unit`/`description`/`group` (#86, decision 23) already carries the descriptive fields owner deliverables name — tag description, engineering unit, plant-area grouping — and the signal index serves them over the monitor.
- **Checkout and test primitives.** Persistent forcing with substituted quality (decision 21, #84) is the loop-check substitution primitive; I/O-health counters and scan-overrun reporting (decision 22, #83) supply the point-health view; the scripted rig tests and checked-in compose rig (decision 49) are the FAT-equivalent engineering evidence; `dcs-model` `validate`/`lint`/`diff`/`schema` plus `--check` are the design-stage verification the testing standards assume [8, 17].
- **Change evidence.** The durable attributed journal (decisions 36, 39) plus `dcs-model diff` give a runtime audit trail and a pre-deployment review surface — the change-evidence shape the sources describe [7 §17; 14], with the lifecycle-side gaps recorded in `docs/research/deployment-commissioning.md`.

What would need contract work or a recorded decision — the gap list implementation tickets would consume:

1. **Owner tag/naming convention as model data.** Points, components, and signals carry ids, names, and display metadata; there is no field for an owner-format tag (the divergent conventions of [10, 18, 20]), no declaration of which convention applies, and no lint check of tag well-formedness or uniqueness. Carrying an optional declared tag plus a naming-convention section is schema work; whether the model stores the owner tag or only exports it into the I/O list is a recorded-decision question.
2. **I/O-list and tag-database interchange.** The model already holds everything an I/O list names — point identity, direction, value kind, device/channel binding, unit, description, group — but nothing emits the owner-format artifact (the Excel template of [13 TEM-00210]) and nothing consumes one. Export is a `dcs-model`-level tooling question; *import* — seeding or reconciling a model from an owner's I/O list or tag database — needs a declared field mapping and merge/validation rules and is the larger contract question [12 §7.9.2, 18, 22].
3. **Parameterized templates beyond one helper.** `pumping_station` is a single fixed composition; there is no general declare-once/instantiate-N template mechanism, and nothing records *which* template, version, and parameter set produced a document — the type/instance traceability the standards and vendor tools assume [3 §5.6; 4 §6.3.6; 25]. A template/provenance layer — and whether provenance lives inside the emitted document — is contract work and a recorded decision.
4. **A bulk-edit seam.** Composition regenerates whole documents; there is no in-place bulk operation — apply a parameter table across instances, or rename under a convention — over an existing model. Whether bulk edit means "regenerate from builder code plus `dcs-model diff` review" or a distinct apply-patch operation on the document is a recorded decision.
5. **Per-tag-class checkout records.** Loop-check forms, inspection test certificates, and C&E runs are external document workflows [8, 13, 23]; nothing binds a checkout run to a model fingerprint (the analog of the deployment note's commissioning-evidence gap), and although `Signal::group` could supply a class axis, no checkout record or lint grouping consumes it.
6. **A defined engineering-deliverable set.** There is no enumerated export set for owner deliverables — I/O list, alarm-database rows, signal-index export — and whether the platform generates owner-format documents or supplies data for the owner's document system is a customer question [13, 15, 19].
7. **P&ID and loop-drawing interop.** IEC 62424-class CAEX exchange with P&ID tools [4] has no counterpart — the platform holds no graphical document model. Recorded as out of scope unless a client names P&ID-tool integration.

## Proposed DCS implications

*All items in this section are proposals, not decided behavior.*

- Keep `dcs-build` composition as the template mechanism rather than adding an in-model template schema: a parameterized builder function is the typical, its config struct the site-specific parameter set, and the emitted `PlantModel` the versioned deliverable — matching how owner typicals are standard specifications instantiated per site [16, 21, 24] and giving compile-time enforcement no schema can. Multiple stations of a type are multiple invocations, consistent with decision 47's one-pair-per-model topology.
- If a client names an owner tag convention, carry it as optional declared metadata on points and components — checked for well-formedness and uniqueness by `dcs-model lint` — rather than baking a convention into the schema: the conventions demonstrably diverge per owner [10, 18, 20], so convention-as-declared-data outlives any one format.
- Propose an I/O-list *export* as the first interchange — a `dcs-model` subcommand emitting a tabular point/channel/signal listing a template can format to an owner's TEM-00210-style artifact — because the model already holds the data [12 §7.9.2]; defer import until a client names the source format and reconciliation rules.
- Treat bulk edit as *regenerate and diff*: modify the builder inputs, emit a new revision, and let `dcs-model diff` produce the review record — the versioned-document discipline that matches owner document control [14] rather than in-place mutation of the artifact under review.
- If template provenance is implemented, record it as generated-by metadata in the emitted document — template id, version, parameter set — extending decision 3's versioning convention instead of maintaining a parallel register [4 §6.3.6's typical identification is the standards-side analog].
- Keep P&ID/loop-drawing exchange out of the model contract; the model exports the tag and I/O data those artifacts consume [4, 11].

## Assumptions needing customer validation

- Which naming convention the first client applies — an ISA-5.1-derived loop scheme [1], an owner-specific fragment format [10, 18, 20], or IEC 81346-style reference designations [3] — and whether the model must *store* owner tags or only *export* them into deliverables.
- I/O-list directionality: export-only from the model, or import/reconciliation from the client's spreadsheet — and in either direction, the client's format and field set [12 §7.9.2; 13 TEM-00210].
- Whether templates must be in-model, client-editable declarations or remain Rust builder code; and whether type→instance provenance inside the document is required for the client's review workflow [25, 26].
- The contractual deliverable set and formats the client must produce — I/O list, master alarm database, C&E matrix, functional descriptions — and whether the platform generates them or feeds the owner's document templates [13, 15].
- Whether per-tag-class checkout evidence must be generated by the platform (a scripted run bound to a model fingerprint) or the client's own site tests suffice — the same open item the deployment note records for commissioning records.
- The scale gate itself: a reference station runs tens of points, where per-point engineering is tolerable; the bulk machinery's acceptance evidence is justified only when the first plant's point count or station count demands it — which no gathered source answers for a first client.
